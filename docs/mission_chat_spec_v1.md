## 2. 힌트 사용과 미션 완료를 분리한다 — **지표 blocker**

v52에서 **힌트 버튼**이 생겼다. 미션마다 모범 문장 하나와 그 번역을 보여 준다(`n7_mission_hint`).

문제는 이렇다. 힌트는 **정답에 가까운 문장**이다. 학습자가 버튼을 누르고 그대로 읽어도 판정 AI는 완료로 볼 가능성이 높다. 그러면 아래 셋이 전부 `mission_completed=true` 로 합쳐진다.

- A. 스스로 만들어 낸 발화
- B. 힌트를 본 뒤 자기 말로 바꾼 발화
- C. 힌트를 그대로 읽은 발화

그런데 이 기능의 성공 정의 2번은 **「학습자가 스스로 말한다」**다. 지금 구조로는 **힌트 도입 뒤 달성률이 올라가도 콘텐츠가 좋아진 것인지 정답 노출이 늘어난 것인지 구별할 수 없다.**

### 필요한 필드
```
hint_used              : bool      # 그 미션에서 힌트를 열었는가
hint_opened_at_turn    : int       # 몇 번째 턴에 열었는가
mission_completed      : bool
completion_after_hint  : bool      # 힌트를 연 뒤에 완료됐는가
mission_evidence       : string    # 완료로 본 실제 사용자 발화
```

### 지표
`independent_completion_rate` 와 `assisted_completion_rate` 를 나눠 본다.
힌트를 그대로 읽었는지(C)까지 보고 싶으면 `mission_evidence` 와 `hint_ko` 의 문자열 유사도를 사후에 재면 된다 — 별도 필드는 필요 없다.

## 3. 미션 상태의 주인을 하나로 정한다 — **대화 품질 blocker**

지금은 **대화 AI가 어떤 미션이 남았는지 스스로 추론**하고, 판정 AI가 따로 `completed_missions` 를 계산한다. 두 시스템이 각자 상태를 갖고 있으니 어느 한쪽이 틀리는 순간 **AI가 이미 끝난 미션을 다시 묻는다.**

> **[2026-09-04 갱신] 「서로를 모른다」는 이제 틀린 말이다 — 주입은 이미 된다.**
>
> 판정 AI 가 낸 `completed_missions` 를 서버가 합집합으로 저장하고
> (`business/chat.py:283-291`), **대화 AI 를 부를 때 시스템 메시지로 넣는다** —
>
>     chat.py:22    {"role":"system", "text":"현재 완료된 미션 : " + missions}
>     chat.py:135   create_chat_history(dialog.prompt, …, chat.completed_missions, True)
>
> **순서도 안전하다.** 앱이 `await checkMission(...)` 을 끝내고 400ms 뒤에 봇 응답을
> 요청한다(`mission-dialog.tsx:251,290`) — 판정이 먼저 저장되고 그다음 봇이 말한다.
> **경쟁이 없다.**
>
> **그리고 「원장 117행을 재저작해야 한다」도 틀렸다.** `mission_detail` 은 이미
> JSON 이다 — `chat.py:59` 가 그것을 그대로 파싱해 앱의 미션 칩으로 넘긴다
> (`[{mission, descr}, …]`). 그러면 **남은 미션 = 전체 라벨 − 완료 라벨**이 서버에서
> 기계로 나온다. `dialog` 도 `chat.completed_missions` 도 이미 `chat.py:133-135` 에
> 있다. **원장도 페르소나도 안 건드린다.**
>
> **그래서 이 절이 살아 있는 이유는 「모른다」가 아니라 「알려주는 방식이 약하다」다.**
> 셋이고 전부 서버 안이다 — `DEV-18` 로 뺐다.
>
> **ⓐ 판정이 실패한 턴은 영영 기록되지 않는데, 봇은 그대로 대답한다.**
>    `checkMission` 이 `null` 이어도 400ms 뒤 `"request"` 가 나가 봇이 말한다
>    (`mission-dialog.tsx:266,290`). 그 턴에 달성한 미션은 목록에 안 들어가고,
>    대화 AI 는 낡은 목록을 보고 **그 미션을 다시 묻는다.**
>    **이 절이 말하는 증상의 가장 직접적인 원인 후보다.**
>
> **ⓑ 완료된 것만 주고 남은 것은 안 준다.** 대화 AI 가 「전체 미션 서술」에서
>    「완료 라벨 배열」을 스스로 빼야 한다. **뺄셈은 AI 가 틀릴 수 있는 자리**이고,
>    위에서 봤듯 서버가 대신 할 수 있다. 아래 제안의 `remaining_missions` 는
>    **그 뺄셈을 없애자**는 뜻이다.
>
> **ⓒ 그 한 줄이 맨 앞에 놓인다.** `create_chat_history` 가 페르소나 → **완료 미션**
>    → 첫 봇 대사 → 대화 전부 → 새 발화 순으로 쌓는다(`chat.py:24-42`).
>    **대화가 길어질수록 그 줄은 현재 턴에서 멀어진다.**
>
> **딸린 것 둘** — `ko_chat.completed_missions` 가 **`String(200)`** 이다(한글 라벨
> 셋이면 여유롭지만 상한이다). 그리고 **`target_grammar_used` 를 리포트에서 쓰는
> 것**이 남았다 — 2026-09-04 에 목표 문법을 판정 프롬프트에 넣고(「완료 조건이
> 아니다」를 같이 못 박았다) 출력에 `target_grammar_used`·`target_grammar_evidence`
> 를 더했고, **원장 값이 판정까지 닿는 것을 실제로 확인했다.** 쓰는 것만 남았다
> (부록 A 의 `P-c`).

프롬프트에 「이미 나온 미션은 다시 묻지 마세요」라고 적어 두는 것보다, **상태를 주입하는 편이 훨씬 강하다.**

### 제안
판정 AI가 매 사용자 발화 뒤에 반환:
```
completed_missions        : [label]
newly_completed_missions  : [label]
remaining_missions        : [label]
evidence_by_mission       : {label: 사용자 발화}
```
다음 대화 AI 호출에 **`remaining_missions` 를 시스템 상태로 직접 넣는다.**

### 같이 정할 것 — 문법은 완료 조건이 아니다
v52부터 방침이 바뀌었다. **목표 문법은 「쓸 수 있게 유도할 것」이지 「반드시 쓰게 만들 것」이 아니다.** 프롬프트에는 「사용자가 뜻이 통하게 말했으면 그 미션은 채워진 것이고 목표 문법을 썼는지는 보지 마라」를 넣었지만, **판정 쪽이 따라오지 않으면 실효가 없다.**

```
mission_completed        : bool     # 뜻이 통했는가 — 진행의 기준
target_grammar_used      : bool     # 별도 관찰값
target_grammar_evidence  : string
```

> **[2026-09-04 갱신] 아래 둘은 들어갔다.** `missionPrompt` 에 `Target Grammar` 슬롯과
> 「이 값으로 status 를 정하지 마세요」를 넣고, 출력 스키마에 `target_grammar_used` ·
> `target_grammar_evidence` 를 더했다(`_normalizeCheckMission` 이 빠진 키를 메운다).
> **`mission_completed` 는 따로 만들지 않았다** — `completed_missions` 배열이 이미
> 그 일을 하고, 프롬프트가 「문법이 틀려도 뜻이 통하면 달성」이라고 이미 말한다.
> **원장의 `target_grammar` 가 판정에 안 닿고 있던 것이 진짜 문제였다** —
> `repo_chat._Dialog` 가 다섯 칸만 노출했다. 이제 닿는다.
대화 진행은 `mission_completed` 로만 판단하고, 문법은 사후 피드백에서 따로 다룬다.
「대화는 잘했는데 목표 문법은 안 썼다」가 그 자체로 유용한 학습 데이터다.

## 4. STT — 오인식 처리

음성 입력이다. 지금 프롬프트에는 「음성 환경이니 짧게 말하라」 한 줄뿐이고 **입력 쪽 규칙이 없다.**

### 알려진 오류
- 「뭐라고요?」에 **인사 미션이 체크**됨 → 판정이 단어 유사도가 아니라 **대화 행위**를 봐야 한다. 「뭐라고요?」는 되묻기(clarification request)이지 인사가 아니다.
- 「김풀리예요」를 **통째로 이름으로 인식** → 완료 여부와 슬롯 값 추출을 분리한다.
  ```
  mission_completed = true
  raw_evidence      = "김풀리예요"
  normalized_value  = "김풀리"
  ```

> **[2026-09-03 갱신] 발음 평가 API 가 이미 서버에 있다.**
> `POST /tutorus/pronunciation`(`api/accepter/tutorus_accepter.py:31`)이
> `score.overall`(30~100) · `weakWords[]` · `weakPhones[]` 를 낸다. `api/.env` 에
> `TUTORUS_*` 6줄이 이미 있고, **기준 문장이 없는 자유 발화를 채점하는 선례까지**
> 있다(`evaluateShadow`, `api/business/tutorus_pron.py:129`). 없는 것은 **앱 배선**뿐이다.
> 그리고 **학습자가 STT 결과를 키보드로 고칠 수 있다**
> (`app/src/components/dialog/dialog-input.tsx:106-109`) — 그래서 전송되는 텍스트는
> 말한 것이 아닐 수 있고, 발음 채점의 기준 문장을 무엇으로 잡을지가 판단거리가 된다.
> **다만 Tutorus 는 dev 엔드포인트·공용 자격증명이고 서버에 ffmpeg 가 필요하다** —
> 운영 승격이 발음 축의 진짜 blocker다.

### 필요한 것
- STT 의 `transcript` · `confidence` · `alternatives` 를 판정 AI에 전달. **confidence 가 낮은 텍스트를 LLM이 그럴듯하게 보정해서 곧바로 완료 처리하는 것을 막아야 한다.**
- 불명확 입력 처리 규칙(프롬프트가 아니라 앱/백엔드 단):
  1회차 → 고정 재요청 「다시 한번 말해 주세요.」 · 2회차 → 더 짧은 질문이나 선택지 · 3회차 → 같은 미션을 계속 밀지 말고 다음 미션으로 이동하거나 다시 말하기 UI 노출.
  ※ 「다시 한번 말해 주세요」는 **v53에서 대화 운영 표현 whitelist 에 넣어** 초급에서도 쓸 수 있게 해 두었다.

## 5. 실패 모드 규칙

지금 어디에도 정의돼 있지 않다. 프롬프트로 일부는 되지만, 반복 횟수 같은 것은 앱이 세야 한다.

| 상황 | 행동 |
|---|---|
| 「네」만 반복 | 같은 질문 반복 금지 → 더 좁은 질문 |
| 「몰라요」 | 다른 방식으로 1회만 유도 → 그래도 실패하면 다음 미션 |
| 침묵 / `...` | 짧게 한 번 재질문 → 선택지 |
| 영어·모국어 사용 | 한국어로 짧게 다시 질문, 계속되면 UI 힌트 |
| 주제 이탈 | 한 번 받아 준 뒤 남은 미션으로 연결 |
| **AI에게 질문** | **질문에 먼저 답한 뒤** 남은 미션으로 — hard rule 로 둘 것 |
| 공격적 발화 | 중립적으로 경계를 세우고 역할극 복귀 |
| 종료 요청 | 즉시 종료 |

「사용자의 질문에 먼저 답하라」는 특히 중요하다. 질문을 무시하고 미션으로 돌아가면 **성공 기준 1번(계속 말하게 만들기)을 직접 해친다.** 실제로 관찰된 문제다 — 사용자의 「왜요?」에 답하지 않고 미션 질문만 던졌다.

### 진척 없는 턴 기준
「8~12턴」 같은 총량보다 **미션별 진척 없는 연속 턴 수**가 낫다.
> 같은 미션에서 사용자 발화가 두 번 연속 진척되지 않으면 질문을 더 직접적으로 바꾼다. 세 번째에도 진척이 없으면 그 미션을 건너뛰고 다른 미션으로 이동한다. 나머지를 다 본 뒤 한 번만 다시 시도한다.

3슬롯이면 **5~8 사용자 턴**이 자연스러운 목표로 보인다. 20턴은 이미 실패로 분류하는 편이 맞다.

## 7. 발화 길이 기준 — 데이터가 모이면

프롬프트가 「한 번에 1~3문장, 120자 이내」로 제한하고 있는데 **근거 없는 숫자**다(v50에서 물려받았다). TTS/STT 대화에서는 글자 수보다 **발화 초 수**가 맞는 기준이다. 감으로는 한 발화 3~7초 정도.
**TTS 로그에서 실제 발화 시간을 모은 뒤에 다시 잡자.** 지금 바꾸면 근거 없는 숫자를 다른 근거 없는 숫자로 바꾸는 셈이다.

# 부록 A — 프롬프트를 역할별로 나눈다 (2026-09-04)

> **여기서부터는 기획자 원문이 아니다.** 위의 §0~§7 은 2026-09-01 의 원문이고,
> 이 부록은 그 뒤에 나온 물음과 그에 대한 조사·제안이다. 섞어 읽지 마라.

2026-09-04 에 기획자가 물었다 — 「**프롬프트를 대화 중에 하나하나 더 나은 문장으로
고쳐주고 틀린 점 짚어주는 AI, 그리고 보고서 내용 만들어주는 AI 이렇게 종류별로
나뉘어져 있어야 하지 않을까 싶어. 배포본도 내가 알기론 그렇게 되어있을걸?**」

그리고 옛 프롬프트 둘을 참고로 주면서 **「이거 그대로 쓰진 마」**, 리포트 쪽은
**「이것도 부족한 점이 많으니까 참고만 하고 그대로 쓰지는 마」**라고 했다.
**A-7 에 원문 그대로 보존한다** — 이 대화에만 두면 또 잃는다.

## A-1. 지금 몇으로 나뉘어 있나 — **셋인데 가운데가 두 일을 겸한다**

| | 어디에 있나 | 무엇을 하나 | 호출 |
|---|---|---|---|
| **대화 AI** | **원장** `ai_persona_prompt` (과마다 다르다) | 다음 말을 만든다 | 발화마다 |
| **판정+코치 AI** | **코드** `xternal/openai.py` `missionPrompt()` | **미션 판정과 문장 교정을 한 번에** | 발화마다 |
| **리포트 AI** | **코드** `xternal/openai.py` `reportPrompt()` | 4축 총평 | 대화 끝에 한 번 |

가운데가 **스스로 그렇게 말한다** — 첫 줄이 「당신은 … **'심판(Referee)'이자
'언어 코치(Coach)'**입니다」다. 기획자의 지적이 맞다.

## A-2. 주신 옛 프롬프트는 **다른 계통이 아니다 — 지금 것의 부모다**

둘을 나란히 놓고 봤다. Part 1~4 의 뼈대, 넷의 판정 기준, `Error/Tip/Perfect` 셋의
정의, 「자소 분리」와 「ㅋㅋ·ㅎㅎ 예외」까지 **글자 단위로 이어진다.**

| | 옛 프롬프트 | 지금 `missionPrompt` |
|---|---|---|
| Input Data | User Level · Current Topic · **Previous AI Question** · **User Input** · Mission List | User Level · Current Topic · Mission List · **Target Grammar**(신규) · **Feedback Language**(신규) |
| 피드백 필드 | `description` | `feedback` (이름만 바뀌었다) |
| 피드백 언어 | 한국어 고정 | **학습자 모국어** · `recommend_example` 만 한국어 |
| 자기 정정 규칙 | 없다 | 있다 (마지막에 정정한 것으로 판정) |
| 출력 구조 | **`mission_result` · `correction_result` 두 객체** | **한 객체로 납작하다** |

**그래서 「나눠야 하지 않나」는 되돌리자는 말이 아니라, 부모에 있던 두 성질이
자식에서 사라진 것을 되찾자는 말이다.** 사라진 둘이 이것이다 —

## A-3. 사라진 둘

### ① 입력 두 칸이 주석으로 빠지고, 대신 **전체 이력**을 보낸다

    openai.py:152    # 일단 이거 두 개는 제외
                     # - Previous AI Question: "{Previous_AI_Line}"
                     # - User Input: "{User_Input_Sentence}"

빠진 자리를 무엇이 메우고 있나 — `business/chat.py:258` 이
`create_chat_history(…, is_system_rule=False)` 로 **첫 봇 대사 + 그때까지의 대화
전부 + 새 발화**를 쌓아 보낸다. 페르소나(`dialog.prompt`)는 안 들어간다.

**한 호출의 입력이 턴 수에 비례해 늘고, 대화 하나의 총합은 턴 수의 제곱으로 는다.**
`max_tokens` 도 없다.

### ② 출력이 한 객체로 납작해졌다

옛 것은 `mission_result`(미션)와 `correction_result`(언어)가 갈려 있었다. 지금은
열 개 남짓한 키가 한 층에 섞여 있다. **미션 판정을 손보면 교정 문구가 같이 흔들리고,
그 반대도 마찬가지다.**

## A-4. 전체 이력이 정말 필요한가 — **규칙을 하나씩 셌다**

「나누면 좋겠다」로 끝내지 않고, 지금 프롬프트의 규칙마다 **어디까지 봐야 판정할
수 있는지**를 적어 봤다.

| 규칙 | 봐야 하는 범위 |
|---|---|
| Part 1-1 Logic Validity | **직전 질문 한 줄** — 프롬프트가 「직전 질문」이라고 스스로 적었다 |
| Part 1-2 Mission Completion | 현재 발화 |
| Part 2-1 `is_context_natural` | 직전 질문 한 줄 + `Current Topic` |
| Part 2-2·3·4 어휘·표기·문법 | 현재 발화 |
| Part 3 status | 위 넷의 결과 |
| Part 4 Self-Correction | **한 발화 안**(그 발화에서 마지막에 정정한 것) |
| Part 4-2 recommend_example | 현재 발화 |

**직전 한 줄을 넘는 것을 요구하는 규칙이 하나도 없다.**

「완료 미션이 쌓이는 것」도 이유가 안 된다 — 판정 AI 는 완료 목록을 **받지도 않고**
(`chat.py:258` 이 `completed_mission=None` 을 넘긴다), 누적은 서버가
`chat.py:283-291` 에서 **합집합으로** 한다. 판정 AI 가 누적할 필요가 없다.

> **다만 「필요 없다」와 「빼도 같은 판정이 나온다」는 다른 말이다.**
> LLM 은 맥락이 줄면 다르게 판단한다. **평가 세트 없이 이력을 걷어내면 안 된다** —
> 이 저장소는 아직 실제 대화를 돌려 본 적이 없다(§처리 순서 6).

## A-5. 옛 리포트 프롬프트 — 나은 점 둘, 그대로 쓰면 안 되는 점 셋

### 나은 점

**① 전체 대화 기록을 본다.** 지금 `create_report` 는 학습자가 **실제로 한 말을
넣지 않는다** — 불리언 넷과 `feedback` 문자열, 그리고 새로 넣은 발음 점수만 넣는다.
**요약의 요약이다.** 총평이 뭉툭한 이유가 여기 있을 수 있다.

**② User Level 을 고려해 「초급자에게 너무 가혹하게 채점하지 마세요」.**
지금 축 값은 앱이 불리언 통과율로 낸다(`mission-report.tsx`) — **레벨 보정이 없다.**
발화가 적을수록 한 번의 실수가 축을 크게 흔든다.

### 그대로 쓰면 안 되는 점

**① `sentence_feedback_list` 를 리포트 AI 가 다시 만든다.** 발화별 코치가 이미
만든 교정문이 있는데 두 벌이 되고, **말풍선과 리포트가 서로 다른 교정을 보여 줄 수
있다.** 지금 방식(발화별 결과를 모아 쓰기)이 이 점은 낫다.

**② `pronunciation` 을 맞춤법으로 정의한다.** 우리는 이제 **실측 발음 점수**가
있다(Tutorus). 옛 정의를 가져오면 그것을 도로 덮는다.

**③ `total_score` 한 숫자.** 무엇으로 어떻게 합쳤는지 알 수 없는 수는
**「4축을 보여 준다」는 이 화면의 취지와 어긋난다.** 축이 넷인데 굳이 하나로
접을 이유를 기획에서 찾지 못했다.

## A-6. 제안 — **넷으로 나눈다**

| | 어디 | 입력 | 출력 |
|---|---|---|---|
| **대화 AI** | 원장 · 과별 | 지금 그대로 | 다음 말. **판정하지 않는다** |
| **심판 AI** | 코드 · 공통 | 미션 목록 · 남은 미션 · 직전 질문 · 발화 | 달성 미션 · 논리 타당 |
| **코치 AI** | 코드 · 공통 | 직전 질문 · 발화 · 레벨 · 목표 문법 | 넷 판정 · status · 교정문 · 이유 |
| **리포트 AI** | 코드 · 공통 | **원문 발화** · 코치 결과 · 발음 점수 · 레벨 | 축별 점수와 코멘트. **문장 목록은 다시 안 만든다** |

**얻는 것 셋** — ① 코치의 입력이 두 줄로 줄어 **A-3-① 의 토큰 문제가 풀린다**
② 채점 규칙과 교정 문구가 서로를 안 흔든다 ③ 코치가 죽어도 미션 진행은 계속된다
(발음에 이미 쓴 계약과 같은 꼴 — `tutorus_pron.evaluateForFreeSpeech`).

**비용** — 호출이 발화당 1회에서 2회로 는다. 다만 코치 입력이 훨씬 작아지므로
**총 토큰은 오히려 줄 수 있다.** 지연은 `asyncio.gather` 로 묶으면 합이 아니라
`max` 다(발음과 이미 그렇게 하고 있다).

### 하기 전에 반드시 있어야 하는 것

**평가 세트다.** 이 변경은 판정 결과를 바꾸고, 판정이 바뀌면 학습자가 보는 색과
문구가 바뀐다. 지금 이 저장소에는 **판정을 대조할 고정 입력·기대 출력 묶음이 없고**,
개발 기계에 `OPENAI_API_KEY` 도 없다. 그래서 **A-8 의 초안은 문서에만 있다 —
코드에 적용하지 않았다.**

## A-7. 참고 원본 — **기획자가 준 옛 프롬프트 둘 (그대로 쓰지 마라)**

> 기획자 말 그대로 — 심판+코치는 **「이건 참고만 하고 이거 그대로 쓰진마」**,
> 리포트는 **「이것도 부족한 점이 많으니까 참고만 하고 그대로 쓰지는 마」**.
> **아래를 복사해 코드에 넣지 마라.** 무엇을 가져오고 무엇을 버릴지는 A-2·A-5 에 있다.

### A-7-1. 옛 심판+코치 프롬프트

````text
# Role Definition
당신은 한국어 학습 앱의 **'심판(Referee)'**이자 **'언어 코치(Coach)'**입니다.
사용자의 발화를 분석하여 미션 달성 여부를 판단하고, 언어적 정확성을 냉정하게 평가하되 피드백은 부드럽게 전달하세요.

# Input Data
- **User Level:** {User_Level}
- **Current Topic:** {Topic_Keyword}
- **Previous AI Question:** "{Previous_AI_Line}"
- **User Input:** "{User_Input_Sentence}"
- **Mission List:** {Mission_List}

# Analysis Guidelines

### Part 1. Mission & Logic Check
1. **Logic Validity:** 사용자의 말이 직전 질문에 대한 적절한 대답인지(동문서답 아님) 확인하세요.
2. **Mission Completion:**
   - 문법이 틀려도 **의미가 통하면 달성(Success)**입니다.
   - **[Mission List]**의 키워드 의도를 달성했는지 확인하세요.

### Part 2. Detailed Linguistic Analysis (True/False 판정)
아래의 엄격한 기준에 따라 4가지 항목을 평가하세요.

**1. is_context_natural (내용/맥락)**
   - 질문의 의도에 맞지 않거나, 흐름이 끊기면 `false`
   - **단답형 금지:** 서술어 없이 명사만 말한 경우 `false` (예: "이름이 뭐예요?" -> "김철수")
   - **문장 완결성:** "~요", "~니다" 등 문장을 끝맺는 어미가 없으면 `false`
   - **높임법:** 상황에 맞지 않게 반말을 사용했으면 `false`
   - 엉뚱한 주제를 말하면 `false`

**2. is_vocabulary_natural (어휘)**
   - 상황이나 문맥에 어울리지 않는 단어를 사용했으면 `false`

**3. is_pronunciation_correct (발음/맞춤법)**
   - 오타가 있거나 철자가 틀렸으면 `false`
   - **자소 분리 판단:** 글자가 구성되지 않고 낱자로 쪼개진 경우(예: ㅎㅏㄴㄱㅜㄱ) `false`
   - **[예외]:** 감정 표현을 위한 의성어(예: ㅋㅋ, ㅎㅎ, ㅠㅠ)는 자소 분리로 보지 않으며 `true`로 인정합니다.

**4. is_grammar_correct (문법)**
   - 조사, 어미 활용, 어순이 틀렸거나 주어-서술어 호응이 안 맞으면 `false`

### Part 3. Final Correction Status (종합 판단)
위의 상세 평가를 종합하여 다음 3가지 중 하나로 결정하세요.

1. **Error:**
   - `is_grammar_correct`가 false이거나, `is_pronunciation_correct`가 false인 경우.
   - 문법/철자 오류로 인해 의미 전달이 안 되거나 명백히 틀린 경우.

2. **Tip:**
   - 문법과 철자는 맞지만(`true`), `is_context_natural`이나 `is_vocabulary_natural`이 false인 경우.
   - **[User Level]**에 맞지 않게 너무 어렵거나 쉬운 표현을 쓴 경우.
   - 상황에 맞지 않는 반말/존댓말을 쓴 경우.

3. **Perfect:**
   - 4가지 항목이 모두 `true`이며, 문법, 뉘앙스, 레벨 모두 완벽한 경우.

### Part 4. Feedback Generation (Coach 역할)
1. **Description (설명):**
   - 전문 용어(자소 분리, 통사 구조 등)를 절대 쓰지 마세요.
   - "조금 어색해요", "이렇게 말하면 더 좋아요"처럼 **부드럽고 완곡한 표현**을 쓰세요.
   - 잘했을 경우(Perfect)에는 빈 문자열(`""`)을 출력하세요.
2. **Recommend Example (교정 예시):**
   - 틀린 부분이 있을 때만, 사용자의 원래 의도를 유지한 **가장 자연스러운 문장 1개**를 제시하세요.

# Output Format (JSON Only)
반드시 아래 JSON 형식을 준수하세요.

{
  "mission_result": {
    "is_logic_valid": true,
    "completed_missions": ["달성한_키워드"] // 없으면 빈 배열 []
  },
  "correction_result": {
    "status": "error" | "tip" | "perfect",
    
    // 상세 평가 데이터 (Boolean)
    "is_context_natural": true,       
    "is_vocabulary_natural": true,    
    "is_pronunciation_correct": true, 
    "is_grammar_correct": true,       

    // 사용자에게 보여줄 텍스트
    "description": "학습자를 위한 부드러운 1줄 피드백 (없으면 빈 문자열)",
    "recommend_example": "교정된 문장 (없으면 null)"
  }
}
````

## A-8. 초안 — **아직 코드에 없다**

기획자가 「프롬프트도 AI한테 일단 쓰라고 해야지」라고 했다. 아래가 그 초안이다.
**A-6 끝의 조건(평가 세트)이 갖춰지기 전에는 코드에 넣지 않는다.**

셋 다 지키는 것 — ① **키 이름은 지금 것을 그대로 쓴다.** 이미 쌓인
`ko_chat_feedback.answer` 를 읽는 코드가 그 이름들이다 ② **`is_pronunciation_correct`
는 「표기」다.** 소리는 Tutorus 가 잰다 ③ **`Previous AI Question` + `User Input`

### A-8-1. 심판 AI 초안

  perfect 이면 빈 문자열.

# Target Grammar

안 썼다고 status 를 낮추지 마세요. 썼으면 근거를 인용하세요.

# Output (JSON only)
{

  "is_vocabulary_natural": true,
  "is_pronunciation_correct": false,
  "is_grammar_correct": true,

**지금과 다른 점** — 미션을 안 본다 · 전체 이력 대신 두 줄을 본다 ·
「표기이지 소리가 아니다」를 프롬프트가 스스로 말한다 ·
「고친 곳만 바꿔라」가 들어갔다(교정문이 원문과 무관해지는 것을 막는다).

(`mission-report.tsx`), 리포트 AI 는 그 축에 붙일 말만 쓴다. 이유 — 같은 숫자를

## A-9. 기획 확정 — 레벨 보정은 없다. 대신 **세는 단위**를 바꾼다 (2026-09-04)

기획자에게 A-8 의 P-a 를 물었고 답이 왔다.

### 결정 ① 레벨 보정을 하지 않는다

> 「**1급이면 조사 오류는 넘어간다던가 그런건 안되지. 틀린건 틀린대로 잡아내야 해.**」

**판정 기준은 급에 상관없이 하나다.** 코치 프롬프트에 「User Level 이면 이 오류는
넘어가라」를 넣지 않는다. 점수를 뒤에서 계수로 곱하는 것도 하지 않는다 —
「나의 문장 피드백」 탭에 빨간 문장이 둘 떠 있는데 축이 78% 로 보이면 **한 화면이
스스로와 어긋난다.**

`User Level` 은 **코멘트의 어조**에만 쓴다(A-8-3 초안이 이미 그렇다).

### 결정 ② 축 점수는 「분량 중 몇 건 틀렸나」로 본다

> 「**뭐 전체 발화 분량 중에서 몇 건 틀렸냐 이런정도로 봐야하지않을까 점수는?**」
> 「**그리고 위의 전부-아니면-전무는 따로 고쳐야할듯**」

지금은 **발화 하나가 전부-아니면-전무**다 — 열 어절짜리 문장에서 조사 하나 틀리면
그 발화의 문법 축은 통째로 0 이고, **오류 하나와 오류 다섯이 같은 0** 이다.
그리고 5발화 대화면 눈금이 0·20·40·60·80·100 뿐이라 **한 발화가 20% 를 흔든다.**

**따로 고친다** — `DEV-17` 로 뺐다. 아래는 그 카드가 풀어야 할 것들이다.

### 이 결정이 부딪히는 것 셋

**① 지금 코치는 건수를 낼 수 없다.** 출력이 축마다 불리언 하나다
(`is_grammar_correct: true|false`). **몇 건인지도, 어디인지도 모른다.**
그래서 「몇 건 틀렸나」는 화면 계산만 고쳐서는 안 되고 **코치 AI 의 출력이 바뀌어야
한다** — A-8-2 초안에 오류 목록을 더해야 한다. 불리언은 **지우지 않는다**(이미
쌓인 `ko_chat_feedback` 행이 그 키를 갖고 있다. 옛 행은 밀도를 낼 수 없으니
「건수 미상」으로 다뤄야 한다).

**② 내용/맥락 축은 셀 수 없다.** 「동문서답」·「단답형」·「문장이 안 끝남」은
**발화 단위 판정**이지 어절 단위 오류가 아니다. 그래서 축 넷의 성질이 셋으로 갈린다 —

| 축 | 세는 법 | 분모 |
|---|---|---|
| 발음 | 음향 점수 평균 (이미 그렇다) | **잰 발화만** |
| 문법 · 어휘 | **오류 밀도** (바꿀 것) | 분량 — 단위가 미정 |
| 내용/맥락 | 발화 단위 통과율 (**이대로가 맞다**) | 전체 발화 |

**넷을 같은 레이더에 그리는데 세는 법이 셋이다.** 이것을 학습자에게 어떻게
설명하느냐가 이 카드의 진짜 어려움이다.

**③ 「분량」의 단위 — 어절로 확정 (2026-09-04)**

> 「**어절 하나 단위로 해야해. 전체 분량중에 틀린 어절이 몇개 이정도는 가능할듯?**」

    문법 · 어휘 축 = 1 − (그 축에서 틀린 어절 수 ÷ 전체 어절 수)

글자와 발화는 버렸다 — 글자는 오류 하나의 무게가 문장 길이에 좌우되고, 발화 단위는
한 발화에 오류가 셋일 수 있어 100% 로 정규화가 안 된다. **조사·어미 오류가 어절에
붙는다**는 것이 한국어에서 어절을 고르는 이유다.

**분모는 기계가 세고, 분자만 AI 가 낸다.** 전체 어절 수는 발화를 공백으로 가르면
나온다 — AI 에게 물을 것이 아니다. AI 는 **틀린 어절이 무엇인지**만 답한다.
이렇게 가르면 AI 가 셈을 틀릴 자리가 없어진다.

**AI 가 인용한 어절이 원문에 없으면 버린다.** 기계가 대조할 수 있는 검사다 —
환각으로 없는 어절을 짚으면 밀도가 조용히 틀어진다.

**남는 가장자리 둘** — ① 한 어절에 오류가 둘이면(조사도 틀리고 맞춤법도 틀림)
**축이 다르면 각 축에서 따로 세고, 같은 축 안에서는 어절 단위로 한 번만 센다.**
② **띄어쓰기 오류는 분모를 흔든다**(「제가밥을」은 1어절로 세지만 실제로는 2어절이다).
다만 띄어쓰기는 **표기 축**이고 표기는 레이더 축이 아니라 말풍선에만 쓰이므로,
분자에는 안 들어가고 분모만 조금 작아진다. **알고 넘어간다.**

## A-10. 오류 데이터의 주인 — **이미 공유하고 있다**

기획자가 이어서 짚었다 —

> 「**어차피 틀린 걸 보고서에서 한번에 정리해줘야 하니까, 뭘 틀렸는지 그 데이터가
> 있어야 하는게 맞지않나? 물론 그렇게 되면 두개의 AI가 서로 데이터를 공유해야겠지만**」

**맞다. 그리고 공유는 이미 하고 있다 — 새로 만들 배관이 아니다.**

두 AI 가 서로를 부르는 것이 아니다. **코치가 `ko_chat_feedback.answer` 에 쓰고,
리포트가 그것을 읽는다.** 지금도 그렇게 돈다 — `create_report`(`openai.py`)가
발화마다 그 행을 열어 네 불리언과 `feedback` 문자열을 뽑아 프롬프트에 넣는다.
**바뀌는 것은 그 칸에 담기는 것이 요약에서 오류 목록으로 바뀌는 것뿐이다.**

### 그래서 원천 하나가 세 곳을 먹인다

| 쓰는 곳 | 무엇에 | 지금 |
|---|---|---|
| 축 밀도 계산 | 틀린 어절 수 | 없다 — `DEV-17` 이 만든다 |
| **「나의 문장 피드백」 탭** | 원문 · 고친 문장 · 이유 | **이미 그린다**(`report-screen.tsx:232-250`) |
| 리포트 총평 | 무엇이 자주 틀렸나 | 불리언만 본다 — 오류 목록을 받으면 「조사가 세 번」처럼 말할 수 있다 |

### ★ 이 결정이 A-5-① 을 푼다

옛 리포트 프롬프트를 그대로 쓰면 안 되는 첫째 이유가 **`sentence_feedback_list` 를
리포트 AI 가 다시 만들어 교정이 두 벌이 되는 것**이었다.

**오류 목록이 코치 결과에 있으면 그 문제가 사라진다** — 리포트 AI 는 목록을
**받아서 요약만** 하면 되고, 말풍선과 오답 노트와 총평이 **같은 하나**를 본다.
A-8-3 초안의 「문장 교정 목록을 새로 만들지 마세요」가 이것으로 근거를 갖는다.

### 코치 출력에 더할 것 (A-8-2 초안 개정)

    "errors": [
      {"axis": "grammar", "eojeol": "되요", "why": "'돼요'가 맞아요"},
      {"axis": "vocabulary", "eojeol": "부딪힐", "why": "이 상황에는 '부딪히게'가 자연스러워요"}
    ]

**불리언 넷은 그대로 둔다** — 이미 쌓인 행이 그 키를 갖고 있고, `errors` 가 없는
옛 행은 **「건수 미상」**으로 다뤄야 한다(밀도 0 으로 넣으면 옛 대화가 전부 만점이 된다).
`axis` 는 밀도를 축별로 가르는 데 쓰고, `eojeol` 은 **원문 대조로 검증한다.**

## A-11. 판정 AI 를 처음 실제로 태웠다 (2026-09-04)

`DEV-16` 이 「**판정 품질은 아직 아무도 안 봤다**」고 적어 둔 그것을 했다.
기획자가 사내 LLM 게이트웨이 키를 `api/.env` 의 `LLM_GATEWAY_API_KEY` 로 넣어 줬다.

### 게이트웨이로 무엇이 되고 무엇이 안 되나

`https://ai-gateway.mathflat.net/v1` · OpenAI 호환. **키는 산다**(`GET /models` 200).
**그런데 OpenAI 모델이 하나도 없다** — Claude 둘 · Gemini 다섯이고 전부 `vibe-` 접두어다.

|---|---|---|
| 판정 · 리포트 · 번역 | **된다** | chat/completions 가 호환된다. `base_url` + 모델 이름만 |

`api.openai.com` 을 본다(`xternal/openai.py:49,69` 가 인자 없이 클라이언트를 만든다).
**그래서 코드는 안 건드리고, 대본으로 판정만 태웠다.**

### ★ 결함 ① 동문서답이 파란 팁으로 떴다 — **고쳤다**

**기획 확정 (2026-09-04)** — 「**동문서답하면 틀렸다고 나와야 됨**」.

안 망가졌다는 것까지 봐야 고친 것이다.

### 결함 ② 교정문이 학습자 의도를 버리고 봇 대사를 복사했다 — **고쳤다**

문장을 요구하는데 의도(축구 물어보기)를 버렸다.

**기획 확정 (2026-09-04)** — 「**동문서답일 때 교정문을 줄 건 아니고, ~~주제와 관련된

**교정이 필요한 사례를 같이 넣은 이유** — 「동문서답에 교정을 안 준다」만 재면

### 남은 것 — `is_logic_valid` 를 아무도 안 읽는다

    is_logic_valid 를 쓰는 곳: 기본값 3곳 + 타입 선언 1곳. 분기 0곳.

status 로 덮었으니 **학습자 화면은 이제 맞다.** 그런데 「**어떤 종류로 틀렸나**」
(동문서답인가 문법 오류인가)는 여전히 아무도 세지 않는다 — 리포트가 「동문서답 3회」
처럼 말하려면 이 값이 필요하다. **`DEV-17` 의 `errors[]` 와 같은 계열이다.**
