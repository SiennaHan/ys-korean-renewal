# BLOCKERS 냉동 절 — 닫혔고, 가리키는 곳이 닫힌 항목뿐인 것

**현재 판정에 쓰지 마라.** 지금 상태는 `docs/status.generated.md`, 실행 목록은
`docs/developer_tasks.md` 가 쥔다. 여기 있는 것은 그때 그랬다는 기록이다.

**옮기는 기준은 「제목이 닫힘」이 아니다.** 2026-09-03 에 세어 보니 제목이 「고쳤다·
끝났다」인 절이 1,186줄인데, 그중 대부분이 **지금도 근거로 인용된다** —
`CLAUDE.md` 가 「`npm install` 하지 마라」의 근거로 `§1` 을 가리키고, `§2` 는 여섯 곳,
`§6-c` 는 여섯 곳이 부른다. **제목은 문제를 말하고 본문은 근거다.**

그래서 실제 기준은 **「가리키는 곳이 있느냐, 있다면 그것도 닫힌 항목이냐」** 다.

| 절 | 인용 | 왜 옮겼나 |
|---|---|---|
| `§4` 받아쓰기 잔재 | **0** | 아무도 안 부른다 |
| `§12` 탈퇴가 표 하나를 빠뜨렸다 | 1 | 부르는 곳(`developer_tasks` 의 `ANONYMIZE_MODELS` 줄)이 **이미 「끝났다」로 닫힌 항목**이라 경위로만 쓰인다 |

> **세는 법을 틀리면 이 판단이 통째로 틀린다.** 처음에 `BLOCKERS(\.md)? *§ *N` 으로
> 셌다가 **백틱을 못 넘어 과소집계**했다 — 이 저장소의 지배적 표기가
> `` `BLOCKERS.md` §12 `` 라서 거의 다 놓쳤다. 「§12 인용 0」이라 판단하고 옮겼는데
> 그루터기를 지워 보는 대조군이 그것을 잡았다. 셀 때는 `[`\s]*` 를 사이에 넣어라.

## 4. 받아쓰기(dictation) 12개는 잔재다 · 판단 불필요 (2026-08-21)

한때 "만들 것인지 버릴 것인지 정해진 적이 없다" 고 적어 두고 여러 문서에서
결정 대기 항목으로 끌고 다녔다. **정할 것이 아니었다** — 예전에 넣었다가
없앤 기능의 잔재다. 실제로 확인한 것 여섯 —

| 확인 | 결과 |
|---|---|
| `module.ts` 의 dictation 12개 | **전부 `is_disabled: true`** |
| 12개의 `code` | **모두 `YK0042` 하나** — 과마다 다른 콘텐츠가 아니라 같은 껍데기를 12번 붙인 것 |
| 그 코드의 문항 | `problem.ts` 에 **0개** |
| 앱의 화면·라우트 | **없다** |
| **배포본**(`korean-master`) | 데이터에만 있고 화면·라우트 **없다** — 지금 서비스에도 없다 |
| **원장** | 받아쓰기 시트도, 그 말이 든 행도 **0** |

붙어 있는 자리는 1급 4~15과 열둘이다. 교재학습 화면은 활동 목록을 코드에 고정된
일곱 줄로 그리므로 `scene_type` 을 보지 않는다 — **애초에 목록에 뜨지도 않는다.**

즉 지금 아무것도 깨져 있지 않고, 새 교재(연세 글로벌 한국어)의 활동 라인업에도
받아쓰기는 없다(`docs/G1_content_gate_v1.html` §4). **결정할 것이 없으므로 이 항목을 닫는다.**

정리할 일이 하나 남는데 급하지 않다 — `module.ts` 의 죽은 행 12개다.
그 파일은 생성기가 만들지 않는 손 관리 데이터라(`build-content.py` 는 `n*.json` 만
만든다) 지우려면 직접 손대야 한다. **콘텐츠 이관을 할 때 같이 치우는 편이 싸다.**

## 12. 탈퇴가 표 하나를 빠뜨리고 있었다 — 고쳤다 (2026-08-29)

<!-- 관찰: api/shared/withdrawal_scope.py, api/business/user_withdraw.py, api/persistence/model.py @ 98d4eba
     — 확인: model.py 에 그 뒤로 늘어난 것은 ko_inquiry.actual·expected 뿐이다 — user_id 가
       없는 표라 이 절의 「user_id 가진 표 열다섯」 셈과 무관하다. 440900f(다른 세션)는
       KoMissionHint 표를 추가했다 — 이 표도 user_id 가 없어 열다섯 셈과 무관.
       98d4eba(DEV-02)는 이미 열다섯에 들어 있던 ko_error_report 에 segment_start(정수)·
       matched_line(자유 텍스트)을 더했다 — 표 자체는 새로 안 늘었지만 「자유 텍스트 둘」
       이 셋이 됐길래 그 문장을 고쳤다(아래) -->
<!-- 왜: 아래 「어느 표가 어느 갈래인가」와 「이 표만 Integer 다」는 그 셋을 읽고 적은 관찰이다 -->

`api/shared/withdrawal_scope.py` 의 `PURGE_MODELS` 에 `KoSignupCodeUse` 가 없었다.
그래서 **기관 발급 코드로 가입한 학생이 탈퇴하면** `ko_signup_code_use` 행이 남고,
그 행의 `user_id` 가 **이미 지워진 `ko_user.id`** 를 가리켰다.

`user_id` 를 가진 표를 모델에서 세어 대 봤더니 **열다섯 중 빠진 것은 이 하나뿐**이었다.
§11 의 「탈퇴 15개 표를 지우고 고아 0」이 맞았던 것은 그때 쓴 학생이 코드로 가입하지
않았기 때문이다 — **대조군이 닿지 않는 곳에 열다섯 번째가 있었다.**

### 정한 것 — 지우지 않고 사람만 지운다

갈래가 둘이었고 **기획이 「행은 남기고 `user_id` 만 NULL 로 비운다」를 골랐다**
(2026-08-29). 지우는 쪽을 안 고른 까닭 둘:

| | |
|---|---|
| ① | **그 표의 존재 이유가 바로 이 경우다.** 모델 docstring 이 따로 두는 까닭으로 「학생이 탈퇴하면 `ko_user` 행이 사라져 흔적이 없어진다」를 든다 |
| ② | **좌석 회계가 영구히 어긋난다.** 탈퇴해도 자리는 안 돌려준다(§10 의 「아직 안 정한 것」 1번). 그래서 `used_count` 는 1로 남는데 행을 지우면 `countUses()` 가 0 을 내고, 둘을 맞춰 볼 근거가 사라진다 |

**NULL 이지 0 이 아니다.** `uq_signup_code_user(code_id, user_id)` 가 걸려 있고 MySQL 은
유니크 인덱스에서 NULL 을 서로 다른 값으로 본다. 묘비값을 썼다면 **같은 코드로 가입한
둘째 탈퇴자가 중복키로 터진다** — 재현에서 그 자리를 따로 눌러 봤다.

### 무엇을 고쳤나

| 층 | 무엇 |
|---|---|
| 경계 | `shared/withdrawal_scope.py` — `ANONYMIZE_MODELS` 를 새로 뒀다. **`PURGE_MODELS` 에 합치지 않았다** — 합치면 "다 지운다" 가 거짓이 된다 |
| 판정 | `business/user_withdraw.py` ③-b. 돌려주는 `deleted` 에 「(user_id 비움)」을 붙여 **지운 수와 비운 수를 이름으로 가른다** |
| 모델 | `persistence/model.py` `KoSignupCodeUse.user_id` → `nullable=True` |
| 마이그레이션 | `api/migration_signup_code_use_anonymize.sql` — **손으로 돌려야 한다.** 기존 표라 `createAllTables()` 가 지나간다(§6-b). 이미 새어 나간 고아를 치우는 `UPDATE` 도 같이 들었다 |
| 어드민 | `business/signup_code_business.listUses` 가 NULL 을 견딘다. `withdrawn` 을 한 칸 더 낸다 — 화면이 「탈퇴한 회원」으로 그릴 수 있게 |
| 문서 | `legal_draft_v1.html` 제4조에 그 예외를 조문으로 적었다 |

**`ids` 를 쓰지 않는 자리가 하나 있다.** 탈퇴 판정은 게스트 id 를 섞은 목록으로 도는데,
`user_id` 를 가진 표 **열다섯 중 이 표만 Integer 다**(나머지 열넷은 `String(45~50)`).
문자열을 섞어 `in_()` 하면 MySQL 이 조용히 0 으로 바꿔 엉뚱한 행을 건드린다. 게스트는
코드로 가입할 수 없으니 애초에 게스트 id 로 된 행이 없다 — 그래서 숫자 하나로만 건다.
같은 이유로 **`user_business._MOVE_PLAIN` 에는 이 표를 더하면 안 된다**(그 자리에 적어 뒀다).

### 돌려서 확인했다 — 대조군을 두었다

`ANONYMIZE_MODELS` 를 비워 **고치기 전과 같은 경로**로 한 번 돌리고, 지금 코드로 한 번
돌렸다. 두 군이 서로 다른 코드를 써서 좌석 회계가 섞이지 않는다.

```
대조군  ANONYMIZE_MODELS = []           → ko_user 사라짐 · use 행 2개 남음 · **고아 +1**
처리군  ANONYMIZE_MODELS = [그 표]      → use 행 3개 그대로 · 둘이 NULL · **고아 0**
        둘째 탈퇴도 통과 (중복키 없음)
좌석    used_count 3 == countUses 3     ← 갈래 1 이었다면 3 vs 0 으로 어긋났을 자리
어드민  listUses 3줄 · 탈퇴 둘은 이름·이메일 None · withdrawn=true · 남은 하나는 이름 그대로
```

**대조군이 증명하지 못하는 것 하나** — 그때도 칸은 이미 `NULL` 허용 상태였다
(마이그레이션을 먼저 돌렸다). 즉 대조군이 보여 준 것은 **범위 목록에서 빠진 것**이
버그였다는 사실이지, 칸의 제약이 버그였다는 것이 아니다. 둘은 다른 얘기다.

### 이어서 정한 것 — 탈퇴자의 학습 데이터 → **§13 에서 했다**

**기획이 방향을 하나 더 냈다(2026-08-29): 「이름을 몇 글자만 남기고 가리되 학습
데이터는 전부 둔다」.** 마스터 어드민은 보고 학교는 못 보게 하려는 것이고, 목적은
학생들이 어떻게 공부하는지 참고하는 것이다. **같은 날 코드로 옮겼다 — §13.**

> ⚠️ **그래서 위 §12 의 전제가 하루 만에 바뀌었다.** §12 는 「탈퇴하면 `ko_user`
> 행이 사라진다」 위에서 고아를 걱정한 것인데, 이제 탈퇴는 계정을 안 지운다.
> **§12 의 코드가 쓸모없어진 것은 아니다** — `ANONYMIZE_MODELS` 는 여전히
> `purgeAccount`(진짜 삭제)에서 돌고, 삭제권 행사가 오면 그 길을 탄다.
> 다만 **탈퇴는 더 이상 §12 의 경로를 지나지 않는다.**

옮기기 전에 답해야 할 것 셋:

1. **이름만 가려서는 식별이 끊기지 않는다.** `ko_user` 행이 남으면 이메일이 남고
   `ko_stt_shadow` 에는 목소리 파일과 전사문 셋이 남는다. 둘 다 이름보다 사람을 더
   확실히 가리킨다. 가릴 것을 이름·이메일·음성까지로 정해야 한다
2. **되돌려 볼 수 있으면 파기가 아니라 가명처리다.** 개인정보보호법에서 가명정보는
   여전히 개인정보이고, 동의 없이 쓸 수 있는 예외(제28조의2)는 통계작성·과학적 연구·
   공익적 기록보존이며 제28조의5 가 **특정 개인을 알아보려는 목적의 처리를 금지**한다.
   「마스터는 누구인지 볼 수 있다」는 그 예외의 조건과 부딪힌다 — **법률 검토가 먼저다**
   (`legal_draft_v1` §01 이 이미 이 항목을 검토 대상으로 남겨 두었다)
3. **표본이 「그만둔 학생」뿐이다.** 학습 참고가 목적이라면 탈퇴자만 모은 데이터보다
   평상시에 쌓는 비식별 집계가 답에 가깝다

내용이 무엇인지도 세어 두었다 — **열다섯 중 여덟은 숫자와 id 뿐이다**
(`ko_learning_record` · `ko_activity_state` · `ko_review_queue` · `ko_study_session` ·
`ko_daily_activity` · `ko_user_flashcard` · `ko_user_flashcard_word` ·
`ko_game_progress`, 다만 마지막은 `extra_data` Text 한 칸을 봐야 한다).
「어떻게 공부하는지」는 전부 이 여덟 안에 있다. 나머지 일곱은 내용 자체가 개인정보다 —
`ko_stt_shadow`(목소리 · 전사문 셋) · `ko_chat_msg`·`ko_chat_feedback`(5000자 자유 발화) ·
`ko_chat`(2000자 리포트) · `ko_inquiry`(회신 이메일 · 2000자 본문) · `ko_inquiry_file`(캡처) ·
`ko_error_report`(자유 텍스트 셋 — DEV-02 가 검색에 걸린 대본 줄을 담는
`matched_line` 을 더했다, 2026-09-01).

### 잡히지 않은 채로 있는 것

**범위 목록이 빠뜨린 것을 잡는 검사가 없다.** 이 버그는 「`user_id` 를 가진 모델이
`PURGE_MODELS` 나 `ANONYMIZE_MODELS` 중 하나에는 있어야 한다」를 한 줄로 세면 잡힌다.
DB 도 네트워크도 필요 없다. 다음에 표가 늘 때 같은 일이 또 난다.
