1활동 상태 머신

모든 학습 활동(게임 제외)이 공유하는 단일 상태 머신. 상태는 활동 단위로 매기고, 그 안의 개별 문항 첫 시도 오답이 복습 큐라는 별도 자료구조에 쌓인다.

복습 큐 예약 기준 = 첫 시도 오답 셸 명세 S1 반영

선택지 활동은 재시도형으로 확정됐다 — 오답이어도 정답을 공개하지 않고 맞힐 때까지 다시 고르게 한다(셸 컴포넌트 명세 §3.3). 따라서 "오답"이 무엇을 가리키는지 못박아 둔다.

  • 복습 큐 예약·정답률·진행 세그먼트 색 — 전부 첫 시도 기준
  • 재시도로 맞혀도 복습 큐에 남는다. 결국 맞혔다는 사실이 첫 시도에 몰랐다는 사실을 지우지 않는다
  • 두 번째 이후 시도는 기록하지 않는다 — 세면 정답률이 항상 100%가 되어 무의미해진다

스트릭 기준 — 활동 1개 완료 확정 · 기존 동작 변경

초안은 "완결한 날에 +1"이라고만 적어 완결이 무엇인지 정하지 않았다. 활동 1개 완료로 확정한다.

다시 풀기를 인정해야 하는 이유: "오늘 할 일"에 복습을 제시해 놓고 그걸 해도 스트릭이 안 오르면 앞뒤가 맞지 않는다.

연습 세션이 빠지는 것은 자동이다 — POST /activity/complete를 호출하지 않으므로(§5-1).

이건 기존 동작을 바꾸는 결정이다

현행 스트릭은 이미 구현돼 있고(business/dashboard.py), 기준은 ko_daily_activity에 그날 행이 있느냐다. 그 행은 saveLearningRecord가 부를 때마다 생기므로 — 지금은 문항 하나만 풀어도 스트릭이 오른다.

활동 1개 완료 기준으로 바꾸면 스트릭이 지금보다 오르기 어려워진다. G1에서 구 학습 기록을 폐기하기로 했으므로 기존 사용자의 스트릭이 줄어드는 문제는 발생하지 않는다.

활동 하나가 평균 5문항(과당 26.7 ÷ 5종)이라 5분 남짓이다. 문항 1개는 너무 헐겁고 과 1개는 너무 무겁다.

2라우트 통일

구 앱은 라우트가 3계열이었다(§역기획서 §3). 신규는 학습 활동 전체를 /learn/{activity} 하나로 모으고, 콘텐츠 ID는 URL에 노출하지 않는다(쿼리는 급·과만).

활동구 라우트신 라우트
단어 학습하기/learn/word?book=&chapter=/learn/word?level=&lesson= 유지(쿼리 키만 급/과로 개칭)
문법 연습/learn/fill-blank?.../learn/grammar?level=&lesson= 개칭
듣고 질문에 답하기/learn/listen-answer?.../learn/listen?level=&lesson=
읽고 질문에 답하기/learn/read-answer?.../learn/read?level=&lesson=
AI 롤플레잉/learn/roleplay?.../learn/roleplay?level=&lesson=
플래시카드/book/chapter/unit/flashcard/$id + .../flashcard/result/$id/learn/flashcard?level=&lesson= — 결과는 셸 공통(§3), 별도 라우트 불필요
AI 미션 대화.../mission_chat/$code + .../dialog/$id + .../dialog/report/$id/learn/mission-chat?level=&lesson= (내부 단계는 쿼리 아닌 컴포넌트 상태로 전환 — 새로고침 시 인트로부터 재개는 허용 가능한 손실)
자모 6종.../{listen-repeat,write,listen-repeat2,read-write,listen,write3}/$code/learn/jamo?level=1&lesson=&sub={1~6} — 6개 하위 유형을 1개 라우트로 통합
게임 5종/main/game/{name}유지 — 학습 활동이 아니라 그대로. VocaShot만 /main/game/vocashot/$pin(호스트/참가) 라우트 제거(§활동 라인업 v2 §4-b)
콘텐츠 ID는 라우트에서 사라진다

구 라우트의 $code(YK0041), $id(C4)처럼 콘텐츠 식별자가 URL에 노출되던 방식은 폐기한다. 신규는 급(level)·과(lesson)만 쿼리로 받고, 실제 문항 목록은 서버가 결정한다 — G1에서 확정한 item_id 체계({'{'}코드{'}'}-{'{'}급{'}'}-{'{'}과{'}'}-{'{'}순번{'}'})는 API 응답 내부 값일 뿐 라우트 파라미터가 아니다.

3플레이어 공통 셸

모든 학습 활동이 공유하는 화면 골격. 콘텐츠 영역만 활동마다 바뀐다.

시각 기준이 바뀌었다 v2.4

초안은 Figma 스타일 가이드를 시각 기준(SoT)으로 삼았다(§3.5). 피그마에 새로 그리지 않기로 하면서 기준이 다음 둘로 옮겨갔다.

  • 활동 UI/UX 목업 — 상태별 화면의 정본. 구현이 다르면 목업이 기준
  • tokens.css — 색·타이포의 유일한 기준. primitive 51 + semantic 30 + 타이포 23

기준 폭도 360 → 390으로 올렸고, 세로는 고정 픽셀 대신 고정 블록 + 가변 밴드로 바꿨다 — 모바일 웹은 주소창 때문에 실제 높이가 기기 스펙보다 작다. 상세는 셸 컴포넌트 명세 §5.1.

3.1 헤더

요소규격
✕ 버튼탭하면 항상 current_item_index 저장 후 이전 화면으로. 확인 다이얼로그 없음(저장되니 안전) — 구 앱의 "저장 없이 나가기"를 완전히 제거
앱바 제목중앙, {급} {과}만 (예: 1급 4과 / Level 1 Lesson 4) v2.4 개정
초안은 {과} · {활동명}이었다. 활동명은 지시문(Title)이 이미 말하고 있어 중복이고, 실제 화면에서 [모음 1] ㅏ,ㅓ,ㅗ,ㅜ…처럼 말줄임으로 잘리고 있었다(자모·플래시카드·미션대화 3곳). 과 제목·학습 대상은 넣지 않는다.
진행 세그먼트바문항 수만큼 분할된 바. 각 세그먼트 상태 4종: 회색 Gray/300(미응답) · 초록 Positive(첫 시도 정답) · 빨강 Destructive(첫 시도 오답 → 복습큐 예약) · Blue/500이고 조금 긴 칸(현재 위치). 높이 6의 얇은 선이라 칸 안에 아이콘이 들어가지 않는다 — 정오답 구분은 피드백 pill 문구와 결과 화면이 담당한다(§7 정정). 결과가 지나온 자리에 남는다 — 구 앱의 점(dot) 진행 표시를 대체. 문항 수에 따라 표시 방식이 바뀐다 — 아래 참조

긴 활동의 진행 표시 플래시카드 확인 반영

세그먼트바는 문항이 많아지면 각 칸이 손톱만 해져 상태를 읽을 수 없다. 실제로 플래시카드는 세트당 10~45장(flashcard_word.ts 실측 — 5번 세트가 45장, 8번이 10장)이라 45칸짜리 바가 나온다.

문항 수표시 방식
1~15개분절바 — 문항 수만큼 칸 분할, 칸 높이 6 · 색만(기본형)
16개 이상연속 진행바 + n/N — 개별 칸을 포기하고 채워지는 바 하나로. n/N은 바 오른쪽에 붙인다(얇은 바 위에는 얹을 자리가 없다)

이 규칙 덕분에 콘텐츠를 세트로 쪼갤 필요가 없다. 45장을 한 세션에 다 못 끝내는 문제는 §1의 이어하기(문항 단위 위치 저장)가 이미 해결하므로, 분량 때문에 세트를 분할하는 설계는 채택하지 않는다.

3.2 피드백 (문항 응답 직후) S1 확정 반영

즉시 채점이다 — 선택지를 누르는 순간 판정한다. 별도 [정답 확인] 동작은 없다.

  • 정답: 세그먼트에 ✓ + Positive · pill "아주 잘 했어요!" · 효과음(축하 연출 없이 소리만) · 하단 [다음] 활성화. 자동 진행하지 않는다 — 기존 디자인이 버튼 활성화 방식이고, 자동으로 넘기면 맞혔다는 확인을 할 틈이 없다.
  • 오답: 세그먼트에 ✕ + Destructive · pill "다시 해보세요" · 선택지가 좌우로 진동(±6px · 300ms) · 효과음. 정답을 공개하지 않고 그 선택지를 비활성으로도 만들지 않는다 — 맞힐 때까지 다시 고른다. 같은 오답을 또 눌러도 진동과 소리가 매번 다시 난다.
  • skip: 헤더 우측, 전 활동 동일 위치. 세그먼트는 회색 유지(오답 처리 안 함) + 해당 문항은 다시 풀기 목록에 skipped 사유로 예약

색만으로 구분하지 않는 이유는 §7(접근성) — 초록–빨강은 적록색각이상에서 구별되지 않으므로 아이콘이 주 신호다. 문구는 §8 대조표를 따른다. 진동 규격과 prefers-reduced-motion 대체안은 셸 컴포넌트 명세 §3.3.

재시도형이 바꾸는 것 — 기록 기준

맞힐 때까지 다시 고르게 하면 정답률이 항상 100%가 될 수 있다. 그래서 첫 시도만 기록한다 — 세그먼트 색·정답률·복습 큐 예약이 모두 첫 시도 기준이며, 재시도로 맞혀도 세그먼트는 빨강으로 남고 복습 큐에서 빠지지 않는다.

3.5 디자인 시스템 — SoT 승격

"Figma 스타일 가이드를 SoT로"를 정정한다 v2.4

초안의 방향은 맞았으나 수단이 틀렸다. 실제로 재보니 가이드는 멀쩡했고 코드가 참조하지 않은 것이 문제였다 — 하드코딩 hex 93개 파일, 임의값 bg-[#......] 998회. 피그마에 변수를 등록하는 것은 간접 처방이다.

확정: 코드의 tokens.css가 SoT다. 가이드의 51색·23타이포 실측값을 primitive / semantic 2단으로 옮겼고, 화면 코드는 semantic만 쓴다(bg-fill-primary · text-text-sub). 피그마 파일은 실측 참조용으로만 남기고 새로 그리지 않는다.

게임의 다크 룩은 별도 시스템이 아니라 같은 토큰의 다크 변형으로 흡수한다 — 다만 학습 화면은 라이트 단일로 확정했다(셸 명세 §6.7).

4다국어 적용 재확인

지시문 병기를 폐지한다 v2.4 개정

초안은 지시문을 한국어 + UI 언어 2줄로 병기했다. 구 앱 화면이 그렇게 돼 있어 따랐던 것인데, UI 언어를 5종 지원하는 이상 한 줄이면 충분하다.

결정적으로 지시문은 조작 안내이지 학습 대상이 아니다. 학습 대상 한국어는 문항·선택지·지문·대화문에 그대로 남아 있고, 거기가 한국어가 있어야 할 자리다. "듣고 맞는 것을 고르세요"는 무엇을 하라는 껍데기 문장이라 학습자가 읽는 언어로만 있으면 된다.

부수 효과로 UI 언어가 ko일 때 같은 문장이 두 번 나오던 문제가 원천적으로 사라진다 — 활동 UI/UX 목업을 만들다 발견한 구멍이었다.

5상태 머신 스트레스 테스트

§1의 상태 머신이 실제 상황을 견디는지 시나리오로 두들겨본 결과다. 12개 중 6개는 v1 스펙에 답이 없었다 — 아래는 그 구멍을 메운 것이며, 표의 "v1 상태" 열이 무엇이 비어 있었는지 보여준다.

#시나리오v1 상태확정 규칙
1완료한 활동을 다시 풀고 싶다(재학습)누락완료 상태는 되돌리지 않는다. 재진입은 "연습 세션"으로 취급 — 진도·스트릭 지표에 영향 없고, 새로 틀린 문항만 다시 풀기 목록에 추가. 완료를 한 번 얻으면 잃지 않는 것이 원칙(진도 지표 안정성).
구현 규칙 4건은 API 스키마 /activity/enter 참조 — 특히 재진입 시 문항 위치를 0으로 되돌려야 한다
2같은 문항을 다시 풀기에서 또 틀렸다누락목록에 남기고 attempts +1. 제거 조건은 정답 1회.
3회 이상 틀린 문항은 세 가지를 받는다 — ⓐ 결과 화면에서 fill-caution 강조 ⓑ 세션에서 먼저 나온다(attempts 내림차순 정렬) ⓒ 상한 밀어내기에서 보호한다(오래됐다고 지우지 않는다).
별도 학습 경로를 새로 만들지는 않는다 — 화면과 로직이 추가되는 데 비해, 위 셋은 이미 있는 attempts 컬럼의 정렬·보호 규칙만으로 된다. 강조만 하고 끝내면 학습자가 할 수 있는 일이 없다는 게 문제였다
3오답 직후 같은 세션에서 바로 다시 풀면 의미가 있나누락S1 확정으로 답이 갈렸다. 선택지형은 맞힐 때까지 진행되지 않으므로 활동이 끝난 시점에 다시 풀 것이 없다 — 결과 화면에 [다시 풀기]를 띄우면 방금 맞힌 걸 또 풀라는 셈이다. 따라서 버튼은 "미해결 항목"이 남는 활동에만 뜬다(플래시카드 "몰라요" · 롤플레잉 재시도 초과 · 건너뛴 문항 · 미션 미달성). 첫 시도 오답은 복습 큐로 가서 다음 날 홈에서 만난다 — 같은 날 반복은 단기기억이라 효과가 얕다
4다시 풀 문항이 계속 쌓여 100개가 넘었다누락보관 상한 60 · 한 세션 10문항으로 나눈다.
구 앱 실측으로 과당 26.7문항(content_counts 1급 12과 평균, 최소 25 · 최대 30)이다. 첫 시도 오답률을 30%로 보면 과당 약 8개가 쌓이고, 60은 7~8과 분량 — 한 급의 절반이다. 상한 자체는 적정하나 60개를 한 번에 보여주면 압도한다.
보관 60(오래된 순 밀어내기, 단 아래 attempts 보호) · 세션 한 번에 10문항 · 홈 카드는 총계 표기(상한 도달 시 "60+"). 세션을 끊으면 "끝냈다"는 감각이 생긴다
5다시 풀 목록에 든 문항이 콘텐츠 개정으로 삭제됐다누락item_id 기준으로 조회 실패 시 조용히 목록에서 제거. 같은 item_id가 수정만 된 경우는 유지(같은 문항으로 간주) — G1의 change_note로 중대 수정은 추적 가능
6B2C 구독이 만료됐는데 잠긴 급의 오답이 목록에 있다누락목록에서 지우지 않고 숨긴다. 재구독 시 그대로 복원 — 결제 이력이 학습 이력을 파괴하지 않게
7게임만 한 날도 스트릭이 유지되나누락유지되지 않는다. 스트릭은 학습 활동(§1 대상 8종) 기준. 게임으로 스트릭을 채우면 학습 회피 경로가 생긴다
8네트워크가 끊긴 채로 활동을 진행했다누락진도·응답을 로컬에 먼저 저장하고 복구 시 서버 동기화. 충돌하면 더 진행된 쪽을 채택(학습자가 푼 것을 잃지 않는 방향)
9진행 중에 앱을 껐다가 다음 날 다시 들어왔다답 있음§1 자기 루프 — current_item_index부터 재개. 만료 기한 없음
10마지막 문항을 오답으로 끝냈다답 있음§1 — 완료 + 다시 풀 문항 보유 상태로 전이
11한 과의 활동을 순서대로 안 하고 건너뛴다답 있음활동 간 선후 제약 없음. 각 활동이 독립 상태를 가진다(과 완료 = 소속 활동 전부 완료)
12AI 미션 대화를 중간에 끊었다부분§1 예외 — 자유 대화라 "3번째 문항"에 해당하는 재개 지점이 없다. 부분 재개를 만들지 않는다 — 대화 요약을 저장해 LLM 컨텍스트를 복원하는 방식은 비용·복잡도가 크고 복원 정확도를 보장할 수 없다. 미션이 3개뿐이라 처음부터 해도 길지 않다.
저장은 하되 용도를 나눈다 — 달성한 미션은 기록용(리포트·복습 큐)으로 저장하고, 재진입 시 진행은 리셋한다. 달성 체크를 남겨 두면 "이미 한 미션을 또 말해야 하나"라는 혼란이 생긴다. 종료 확인 다이얼로그로 사전 안내한다(§6)
연습 세션은 어떻게 들어가고, 뭐라고 부르나

완료한 활동을 다시 풀 수 있게 하려면 진입 경로와 이름이 필요하다. 시나리오 1은 "되돌리지 않는다"만 정했고 이 둘은 비어 있었다.

항목확정
진입활동 목록에서 완료된 활동을 그대로 탭한다. 별도 화면을 만들지 않는다 — 서버가 isPractice: true로 응답하고 셸이 처음부터 시작한다
이름활동 목록에서는 "한 번 더". 결과 화면의 "다시 풀기"와 구분한다

이름을 나눠야 하는 이유: "다시 풀기"는 §8 용어표에서 복습 큐(틀린 문항만)에 이미 배정돼 있다. 완료 활동 전체를 다시 푸는 것과 틀린 것만 다시 푸는 것은 다른 행동이라, 같은 말을 쓰면 학습자가 무엇이 나올지 예상할 수 없다.

두 문구는 서로 다른 화면에 나오므로(활동 목록 / 결과 화면) 충돌이 크지는 않다. 다만 "한 번 더"는 활동 목록에 있어 셸 밖이라, 이번 i18n_player_shell.ts(55키) 범위에는 들어 있지 않다 — 목록 화면 작업 때 함께 등록한다.

12번만 예외 처리가 다르다 — 이유

AI 미션 대화는 LLM과의 자유 대화라 "3번째 문항"에 해당하는 재개 지점이 없다. 그래서 이 활동만 ✕ 종료 시 확인 다이얼로그를 띄운다("대화가 처음부터 시작돼요"). §3.1에서 "확인 다이얼로그 없음"을 원칙으로 세웠지만, 저장할 수 없는 것을 저장한 척하지 않기 위한 의도적 예외다.

상태발생 조건셸 동작

판정이 계속 실패자모 쓰기(OCR)·말하기(STT)에서 반복 실패 3회 실패 시 건너뛰기를 명시적으로 안내한다(state.canSkip). 맞힐 때까지 진행되지 않는 규칙은 선택지가 유한할 때만 안전하고, 후보가 무한한 활동은 판정 오류로 갇힐 수 있다. 새 탈출구가 아니라 이미 있는 헤더 →를 알려 주는 것이다
녹음 실패·무음STT 결과 없음오답 아님. "다시 말해 주세요"로 재시도. §3.4대로 2회 초과부터 다시 풀기 목록 예약
브라우저 뒤로가기학습자가 시스템 뒤로가기✕와 동일 동작(위치 저장 후 이탈). 12번 활동만 확인 다이얼로그

7접근성 — v1의 실제 결함

색만으로 정보를 전달하고 있었다

v1 §3.1의 진행 세그먼트바는 정답과 오답을 색으로만 구분했다. 색각 이상 학습자는 자신이 무엇을 틀렸는지 알 수 없다. 게다가 플래시카드에서는 같은 색이 다른 뜻(알아요/몰라요)이라 색의 의미가 활동마다 달라지는 문제도 있었다.

수정 v3.5 — 아이콘을 진행바에 넣지 않는다. 진행바를 높이 24 → 6으로 줄였다(사각형 줄이 화면 위쪽을 무겁게 만든다). 6px에는 아이콘이 들어가지 않는다. 초록–빨강은 적록색각이상(남성 약 8%)에게 구별되지 않으므로, 정오답의 권위 있는 표시를 다른 곳으로 옮긴다:

  • 문항 화면 — 피드백 pill의 문구("아주 잘 했어요!" / "다시 해보세요"). 색이 아니라 글자다.
  • 결과 화면 — 오답 목록의 [오답 N] 칩 + 고른 답 + 해설. 전부 글자다.

진행바는 "어디까지 왔나"가 주된 일이고 정오답은 보조 신호로 남긴다 — 진행률을 주 지표로 올린 결정(구현 사양 §8)과도 맞는다. 현재 위치는 색이 아니라 칸 길이 10으로 구분한다.

  • 진행 세그먼트에 aria-label: "3번 문항, 정답" / "4번 문항, 오답" — 스크린리더로 진행 상황 파악 가능
  • 스크린리더는 진동·효과음을 받지 못한다. 오답 pill을 aria-live로 두되, 같은 문구를 반복 고지하려면 영역을 비웠다 다시 채운다(동일 텍스트는 재고지하지 않는 리더가 있다).
  • prefers-reduced-motion: reduce일 때 진동 대신 테두리 200ms 1회 깜빡으로 대체 — 현재 코드에 이 분기가 하나도 없다.
  • 피드백은 색 변화만이 아니라 텍스트로도 명시("정답이에요" / "정답은 ○○예요")
  • 탭 대상 최소 44×44pt (구 앱 O/X 버튼은 충분, 세그먼트바는 탭 대상 아님)

8용어와 문구 — 내부 언어를 화면에 내보내지 않기

v1의 문제

"복습 큐에 담겼어요"를 화면 문구로 썼다. 큐(queue)는 개발 용어이고, 한국어를 배우는 초급 학습자에게 "복습 큐"는 이해 불가에 가깝다. 이 문서 전반의 복습 큐·복습 권장·미학습은 전부 내부 용어이며, 화면에는 아래 대조표의 오른쪽만 나간다.

8-b. 번역 검수 — 55키 전부가 아니라 11키만

셸 UI 문자열은 55키 × 5언어 = 220개다. 전부 보라고 하면 아무도 안 본다. 기계적으로 옮겨도 되는 것과 뉘앙스가 실제로 갈리는 것을 나눈다.

키왜 위험한가
toPractice · practiceAgain · homeCardTitle · sessionTitle practice / review 뉘앙스가 언어마다 다르다. 한국어 "다시 풀기"가 en Practice again인데, 일본어·중국어에서 "복습"과 "연습" 중 무엇이 자연스러운지 갈린다
tryAgain · wellDone · perfect 격려 문구다. 직역하면 어색하거나 과한 언어가 있다. en Nice!과 ko 아주 잘 했어요!는 길이·톤이 이미 상당히 다르다
hardItem"자주 틀려요" — 학습자를 탓하는 어감이 되기 쉽다
micDenied · exitConfirmChat 가장 긴 문장 둘이다. 자연스러움도 문제지만 레이아웃이 깨지는지도 여기서 판가름난다
lessonTitle 급·과 표현이 언어권마다 다르다 — Level 1 Lesson 4 / 1級 4課 / 1级 第4课 / Cấp 1 Bài 4

11키 × 5언어 = 55문자열이면 앉은자리에서 볼 수 있는 분량이다. 나머지 33키(next · exit · loading 등)는 기계적 대응이라 후순위로 둔다.

검수는 개발과 병행해도 된다 — 릴리스 전까지만 반영되면 되고, 키 이름은 바뀌지 않는다.

첫 번째에 이름을 붙이지 않는 것이 핵심이다 — 버튼으로 만들면 두 번째와 헷갈리는데, 실제 동작은 선택지를 다시 누르는 것이라 라벨이 붙을 자리가 없다.

9-b. 문구 원칙

  1. 시스템 구조를 설명하지 않는다. 학습자는 큐·상태·세션을 알 필요가 없다. 무엇이 일어났고 다음에 뭘 하면 되는지만 말한다.
  2. 문항마다 토스트를 띄우지 않는다. v1은 오답마다 토스트를 띄우게 돼 있었는데, 10문항 중 6개를 틀리면 토스트가 6번 뜬다. "다시 풀 문제 3개"는 결과 화면에서 한 번 말하는 것으로 충분하다.
  3. 숫자로 말한다. "복습이 필요해요"(모호) 대신 "다시 풀 문제 3개"(행동 가능).
  4. UI 언어가 곧 학습자의 모국어다. 학습 대상 한국어(§4)를 빼면 모든 문구는 학습자 언어로 나간다 — 한국어 문구는 5개 중 하나일 뿐이며, 기본 언어는 영어다.
