개발 명세 §3에 경로와 동작만 있고 필드 계약이 없어서, 그대로 두면 프론트·백엔드가 서로 다른 이름으로 구현할 수 있습니다. 기획에서 먼저 초안을 잡은 것이니 고칠 부분은 고쳐 주세요 — 백지에서 논의하는 것보다 빠를 것 같아 씁니다.

0. 공통 규칙 — 기존 코드에서 확인한 것

새로 정한 게 아니라 현행 koreanapi가 이미 쓰고 있는 방식입니다. 신규 API도 여기 맞춥니다.

makeResponse()를 신규 API에도 그대로 쓰면 값이 섞일 수 있습니다
def makeResponse(data: object):
  response = CommonResponse   # 모듈 전역 dict를 그대로 참조
  response["data"] = data     # 같은 객체를 매 요청이 덮어씀

동시 요청이 겹치면 A 요청의 응답에 B 요청의 data가 실릴 수 있습니다. dict(CommonResponse)로 복사하거나 매번 새로 만드는 편이 안전합니다. 기존 API 전체에 해당하는 문제라 Phase 0에서 같이 보시면 좋겠습니다.

연습 세션에서 지켜야 할 것 4가지

완료한 활동을 다시 풀어볼 수 있어야 한다는 요구가 있습니다. 완료 기록은 남기되 재도전은 열어 두는 방식인데, 그냥 두면 어긋나는 지점이 있습니다.

#규칙안 지키면
1isPractice면 currentItemIndex를 0으로 돌려줍니다. 저장된 값이 아니라 항상 0 저장값이 마지막 위치(예: 10)라 들어가자마자 결과 화면이 뜹니다
2연습 중에는 PATCH /activity/progress를 호출하지 않습니다 원래 완료 기록의 위치가 연습 진행에 덮입니다
3POST /activity/complete도 호출하지 않습니다. 결과 화면은 클라이언트가 이번 세션 값으로 그립니다 completedAt과 correctCount가 덮여 최초 기록이 사라집니다
4POST /learning-record는 호출합니다 — 연습에서 새로 틀린 문항은 다시 풀기 목록에 들어갑니다(G2 §5-1) 연습이 학습에 아무 영향을 못 줍니다

정리하면 연습 세션은 읽기 전용에 가깝고, 예외가 4번 하나입니다.

정답률은 갱신하지 않습니다 — 확인 부탁드립니다

연습에서 더 잘 풀어도 correctCount는 최초 기록 그대로 둡니다. "첫 시도 기준"이라는 원칙과 일관되고, 무한 연습으로 100%를 만드는 걸 막습니다.

대신 학습자는 "다시 풀어서 다 맞혔는데 왜 8/10이지?"라고 느낄 수 있습니다. 그게 문제가 되면 lastPracticeAccuracy 같은 컬럼을 따로 두는 방법이 있는데, Phase 1 범위를 넘습니다. 이번엔 갱신하지 않는 쪽으로 두고 반응을 보는 게 어떨까 합니다.

활동unresolvedCount에 들어가는 것

플래시카드"몰라요" 카드 + 건너뛴 카드
AI 롤플레잉재시도 2회 초과로 넘어간 턴 + 건너뛴 턴
AI 미션 대화 달성 못 한 미션 키워드. 다만 [다시 풀기]의 동작이 다릅니다 — 미해결 항목만 고르는 게 아니라 이전 대화 스레드를 지우고 처음부터 다시 대화합니다.
API는 이미 있습니다 — POST /dialog/{dialogId}/reset (api/chat.ts의 resetDialog()). 현재 이걸 부르는 화면이 하나도 없어 사실상 죽어 있습니다. 결과 화면의 [다시 풀기]에 연결하면 됩니다
발음 자모 sub=1·3 건너뛴 문항만. 진행을 막지 않으므로 오답이 남지 않는다
발음 활동은 정답률에서만 빠집니다 — 진행률에는 들어갑니다

자모 sub=1(자모 듣고 따라하기) · sub=3(단어 듣고 따라하기)는 STT 판정을 쓰지만 진행을 막지 않고 채점하지도 않습니다(구현 사양 §6). 그렇다고 활동에서 통째로 빼는 것은 아닙니다 — 풀었는지 안 풀었는지는 셉니다.

  • totalItems · answeredCount — 정상적으로 셉니다. 진행률 "푼 문항 15/18"이 그대로 나옵니다.
  • gradedCount — 0입니다. 결과 화면의 정답률이 "—"가 됩니다.
  • correctCount · firstTryWrongCount — 세지 않습니다. 복습 큐에도 넣지 않습니다.
  • unresolvedCount — 녹음하지 않고 넘긴 문항을 셉니다(건너뛰기와 같게).

플래시카드도 gradedCount = 0입니다 — 자기 평가라 정오답이 없습니다. 답안 제출 시 isCorrect는 그대로 받되 집계에 반영하지 않습니다. 기록을 남겨 두면 나중에 STT 정확도를 점검할 때 쓸 수 있습니다.

건너뛰기를 빼먹으면 안 됩니다. 헤더의 → 건너뛰기가 상시 있어서, 선택지형에서도 건너뛴 문항이 있으면 unresolvedCount > 0이 됩니다. "선택지형은 항상 0"이 아닙니다.

2. 학습 기록

POST/learning-record확장

기존 엔드포인트입니다. 요청은 그대로 두고 응답만 넓힙니다.

Request — 변경 없음

{ "bookId": 1, "chapterSeq": 4, "menuType": "fill-blank",
  "questionId": 231, "selectedAnswer": "오", "isCorrect": false }
호출 규칙이 바뀝니다 — 문항당 첫 시도에 딱 한 번

재시도형이라 학습자는 맞힐 때까지 여러 번 고릅니다. 그런데 기록은 첫 시도만 합니다 — 전부 세면 정답률이 항상 100%가 되어 의미가 없어집니다.

  • 클라이언트는 첫 응답에서만 호출합니다
  • 서버는 (userId, bookId, chapterSeq, menuType, questionId)로 upsert 해서, 중복 호출이 와도 첫 값이 덮이지 않게 하는 편이 안전합니다
  • 현재 fill-blank는 오답을 아예 저장하지 않습니다(정답 분기 안에서만 호출 + isCorrect:true 하드코딩). 이게 고쳐져야 아래 reviewQueued가 동작합니다 — Phase 0 항목

Response data — 확장

필드타입설명

reviewQueuedbool이번 호출로 다시 풀기 목록에 들어갔는지

구 앱 실측으로 과당 26.7문항입니다. 첫 시도 오답률 30%면 과당 약 8개가 쌓이고, 보관 상한 60은 7~8과 분량입니다. 상한 자체는 적정하지만 60개를 한 번에 내보내면 학습자가 압도됩니다.

숫자어디에
60 — 보관 상한초과 시 오래된 것부터 삭제. total로 노출
10 — 한 세션items에 담아 내보내는 개수(limit 기본값)

정렬은 attempts 내림차순 → createdAt 오름차순입니다. 여러 번 틀린 문항이 먼저 나옵니다.

밀어내기에서 attempts >= 3은 보호합니다 — 자주 틀린 문항을 "오래됐다"는 이유로 지우면 정확히 반대 효과가 납니다.

문항 본문은 여기 담지 않습니다 — 다시 풀기 세션이 기존 문항 조회 경로를 그대로 씁니다. 이 판단이 맞는지 확인 부탁드립니다.
