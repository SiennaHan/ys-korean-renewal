Phase 1의 범위와 전제

콘텐츠 없이 셸만 먼저 만든다. 새 교재 콘텐츠(1급)는 아직 저작 중이므로, Phase 1은 구 앱 콘텐츠를 그대로 꽂은 채 셸·상태·라우트만 교체해 검증한다. 콘텐츠 교체는 Phase 2다.

따라서 이 문서는 콘텐츠 스키마를 건드리지 않는다 — 기존 ko_learning_record의 question_id(Integer)를 그대로 쓰고, Phase 2에서 새 item_id 체계로 이관한다.

셸을 피그마에 그리지 않고 명세대로 바로 구현한다. 규격은 구현 사양에 있다 — 기준 폭 390, 세로는 고정 블록 258 + 가변 밴드, 선택지 173×96, 하단 버튼 358×56.

시각 기준은 기획이 만든 HTML 목업이 담당한다 — 이 문서와 함께 전달된다. 목업은 상태별 화면을 전부 담고 있으므로 구현 대상의 정본으로 삼는다.

대신 두 가지가 필수가 된다. ① tokens.css — 디자인 파일이 SoT가 아니므로 코드의 토큰이 유일한 기준이다. ② Storybook — 구현한 뒤 목업과 대조하고, 이후 수정 요청을 주고받는 통로다. 실제 앱에서는 오답·마이크 거부·로드 실패를 재현하기 어렵다.

Phase 0(보안 핫픽스)은 이 문서와 독립이며 먼저 또는 병행해도 된다.

2DB 신설

기존 명명 규칙(ko_ 접두, user_id는 게스트 겸용 String(45), FK 없이 논리 참조)을 그대로 따른다.

2.1 ko_activity_state — 활동 상태 신설

현재는 활동 완료를 learning_record 건수와 content_counts.TOTAL_QUESTIONS를 비교해 매번 계산한다. G2 상태 머신은 명시적 상태와 이어하기 위치가 필요하므로 별도 테이블로 승격한다.

CREATE TABLE ko_activity_state (
  id                  INT          NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id             VARCHAR(45)  NOT NULL,
  book_id             INT          NOT NULL,      -- 급 (화면 라벨만 "급", 컬럼명 유지)
  chapter_seq         INT          NOT NULL,      -- 과
  menu_type           VARCHAR(20)  NOT NULL,      -- 기존 값 그대로 사용 (아래 §2.2 참조)
                                                  -- word | fill-blank | listen-answer | read-answer
                                                  -- | roleplay | flashcard | mission-chat | jamo(신규)
  state               VARCHAR(16)  NOT NULL DEFAULT 'in_progress',  -- in_progress | completed
                                                  -- ※ 미학습은 행 자체가 없는 상태로 표현(G2 §9: 화면에도 표기 안 함)
  sub                 TINYINT      NOT NULL DEFAULT 0,   -- 하위 유형. 자모만 1~6, 나머지 활동은 0
  current_item_index  INT          NOT NULL DEFAULT 0,   -- 이어하기 위치
  total_items         INT          NULL,                 -- 전체 문항 수. 진행률의 분모
  answered_count      INT          NOT NULL DEFAULT 0,
                                                  -- ※ 응답한 문항 수. 진행률의 분자. 정오답 무관, 발음도 센다
                                                  --    건너뛴 문항과 녹음 없이 넘긴 발음 문항은 세지 않는다
  graded_count        INT          NOT NULL DEFAULT 0,
                                                  -- ※ 채점 대상 문항 수. 정답률의 분모
                                                  --    발음(자모 sub=1·3)과 플래시카드는 0 → 화면에 "—"
  correct_count       INT          NOT NULL DEFAULT 0,
                                                  -- ※ 첫 시도 기준. 재시도로 맞힌 것은 세지 않는다(셸 명세 S1)
  completed_at        DATETIME     NULL,
  created_at          DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()),
  updated_at          DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()) ON UPDATE UTC_TIMESTAMP(),
  UNIQUE KEY uq_state (user_id, book_id, chapter_seq, menu_type, sub),
  KEY ix_user (user_id)
);
sub가 없으면 자모 6종이 같은 행을 쓴다

자모는 라우트가 /learn/jamo?sub=1~6로 6개 하위활동인데 menu_type은 jamo 하나다. 키에 sub가 없으면 다섯이 한 행을 공유해서, 하나를 완료하면 나머지도 완료로 보이고 이어하기 위치가 서로 덮인다.

menu_type을 jamo-1~jamo-5로 쪼개지 않는 이유: 그러면 ko_learning_record·ko_daily_activity·content_counts의 키가 전부 5개씩 늘어난다. sub는 자모에만 의미가 있고 나머지는 0이라 기존 코드가 영향을 안 받는다.

NULL이 아니라 NOT NULL DEFAULT 0인 이유 — MySQL은 UNIQUE 키에서 NULL을 중복 허용하므로, NULL로 두면 자모 아닌 활동의 유니크 제약이 무력해진다.

"복습 권장"은 컬럼이 아니다

G2 §1에서 복습 권장은 완료의 하위 표시로 정의했다. 따라서 state에 값을 추가하지 않고, ko_review_queue에 해당 활동 소속 항목이 남아 있는지로 판정한다 — 상태를 두 곳에 쓰면 어긋난다.

채점은 첫 시도만 기록한다 셸 명세 S1 반영

선택지 활동은 재시도형으로 확정됐다 — 오답이어도 정답을 공개하지 않고 맞힐 때까지 다시 고르게 한다. 따라서 무엇을 기록하는지가 모호해질 수 있다.

  • correct_count · ko_learning_record · 진행바 칸 상태 — 전부 첫 시도 기준
  • 두 번째 이후 시도는 기록하지 않는다 (정답률이 항상 100%가 되어 무의미해진다)
  • ko_review_queue 예약도 첫 시도 오답 기준 — 재시도로 맞혀도 복습 큐에 남는다

즉 문항당 정확히 한 번만 기록된다. 재시도 횟수를 남기고 싶으면 별도 컬럼이 필요하지만, Phase 1 범위 밖이다.

2.2 menu_type 값은 바꾸지 않는다 v1.1 정정

v1 초안의 오류

초안에서 menu_type을 grammar · listen · read로 적었다. 이는 라우트 개칭(§4)을 DB 값에까지 잘못 확장한 것이다. 기존 ko_learning_record·ko_daily_activity·content_counts.TOTAL_QUESTIONS가 전부 fill-blank · listen-answer · read-answer를 키로 쓰고 있어, 값을 바꾸면 기존 학습 기록이 통째로 미아가 되고 진행률 계산이 깨진다.

확정: 라우트(사용자에게 보이는 주소)만 개칭하고, menu_type(내부 저장 값)은 그대로 둔다. 화면 라벨 "권→급"과 같은 원칙 — 표기와 스키마를 분리한다.

2.2-b ko_daily_activity — 스트릭 기준 변경 기존 테이블

스트릭은 이미 있고, 기준을 바꾼다

현행 스트릭은 business/dashboard.py의 _calculateStreak()가 ko_daily_activity에 그날 행이 있는지로 계산한다. 그 행은 saveLearningRecord → updateLastStudy → ensureExists 경로로 만들어지므로, 지금은 문항 하나만 응답해도 스트릭이 오른다.

확정 기준: 활동 1개 완료(또는 다시 풀기 세션 완주). 아래처럼 바꾼다.

대상변경

2.3 ko_review_queue — 다시 풀기 목록 신설

CREATE TABLE ko_review_queue (
  id            INT          NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id       VARCHAR(45)  NOT NULL,
  book_id       INT          NOT NULL,
  chapter_seq   INT          NOT NULL,
  menu_type     VARCHAR(20)  NOT NULL,
  sub           TINYINT      NOT NULL DEFAULT 0,     -- 활동 상태와 같은 규칙
  question_id   INT          NOT NULL,     -- Phase 1은 기존 체계 유지. Phase 2에서 item_id로 이관
  reason        VARCHAR(16)  NOT NULL,     -- wrong | skipped | unknown(플래시카드 "몰라요")
  attempts      INT          NOT NULL DEFAULT 1,
  available_at  DATETIME     NOT NULL,     -- 홈 목록 노출 시각 = 오답 다음 날 0시(KST). 결과화면 [다시 풀기]는 이 값 무시
  created_at    DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()),
  updated_at    DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()) ON UPDATE UTC_TIMESTAMP(),
  UNIQUE KEY uq_queue (user_id, book_id, chapter_seq, menu_type, sub, question_id),
  KEY ix_user_avail (user_id, available_at)
);
규칙 (G2 §6)구현
같은 날 재출제 방지available_at = 오답 발생일 다음 날 KST 00:00. 홈 목록은 available_at <= now만 노출, 결과 화면 [다시 풀기]는 무시하고 즉시 출제
제거 조건다시 풀기에서 정답 1회 → 행 삭제
재오답attempts += 1, available_at 갱신. 3회 이상은 ⓐ 결과 화면 강조 ⓑ 세션에서 먼저 출제 ⓒ 밀어내기 보호
상한 · 세션보관 60(초과 시 created_at 오래된 것부터 삭제, 단 attempts ≥ 3 보호) · 한 세션 10문항 · 홈 카드는 보관 총계(60 도달 시 "60+")
과당 26.7문항 실측 기준으로 60은 7~8과 분량 — 상한은 적정하나 한 번에 내보내면 압도한다
정렬attempts 내림차순 → created_at 오름차순. 여러 번 틀린 문항이 먼저
콘텐츠 삭제 대응조회 시 문항이 없으면 조용히 행 삭제 후 다음 항목으로
잠긴 콘텐츠(B2C)행은 유지하고 노출만 제외. 재구독 시 자동 복원

5.1 Storybook 신설

목업을 대체하는 것이 아니라 구현 결과를 목업과 대조하는 도구다. 셸 컴포넌트 9종만 올린다. 나머지 화면은 이미 있으므로 대상이 아니다. 셸 명세 §3의 상태표가 그대로 스토리 목록이라 새로 설계할 것이 없다.

컴포넌트스토리
ProgressBar2모드(segment ≤15 / continuous ≥16) × 4상태
ChoiceGroup3배치(2·3·4개) × 4상태 + 오답 진동
FeedbackLayer3상태
ResultScreen3상태(perfect · hasWrong · reviewDone)
StateView5상태(로딩 · 실패 · 음성없음 · 마이크거부 · 종료확인)
MicZone · ChatThread · FlipCard · WritingCanvas기본 + 응답 후
전역 토글 2개가 필수다
  1. UI 언어 5종(en·ko·ja·zh·vi) — §7의 "가장 긴 문자열" 검사가 클릭 한 번이 된다. 없으면 그 검사는 사실상 수행되지 않는다.
  2. 뷰포트 360 / 320 — 320에서 선택지 칸 높이가 96 → 72로 줄어야 한다.

이 두 축이 없으면 Storybook이 "컴포넌트 카탈로그"에 그치고, 도입한 이유의 절반이 사라진다.

5.2 컴포넌트 구조

<ActivityShell>                     // 상태·진행·종료를 전담. 활동은 콘텐츠만 렌더
  ├─ ShellHeader                    // ✕(위치 저장 후 종료) · 활동명 · 진행 표시
  │    └─ ProgressBar               // 높이 6 얇은 선. ≤15 분절(색만) / ≥16 연속바 + 옆에 n/N
  ├─ <slot> 활동 콘텐츠              // 활동별 컴포넌트가 들어오는 자리
  ├─ FeedbackLayer                  // 하단 가운데 pill(hug×36) — 정답/오답 문구
  └─ ResultScreen                   // 정답률 · 오답+해설 목록 · [다시 풀기] · [다음 활동]

규격·좌표·상태 목록은 구현 사양에 있다 — 기준 폭 390(360·320 지원), 고정 블록 258 + 가변 밴드, 선택지 173×96.

5.3 활동별 분기 (G2 §3.4)

활동셸에 필요한 분기
단어 · 문법 · 듣기 · 읽기없음. 선택지 수는 2~4개 가변(데이터에서 받음) — 1과 2지선다, 3과 3지선다가 실제로 섞인다
플래시카드진행바 색 의미 교체(파랑=알아요 / 노랑=몰라요 — 자기 평가라 의미색을 쓰지 않는다). 과당 최대 45장이므로 연속바 경로가 반드시 동작해야 함

AI 미션 대화진행 단위가 문항이 아니라 미션 키워드 3개. 결과는 기존 리포트 화면 유지. ✕ 종료 시 확인 다이얼로그(재개 불가)
자모쓰기 유형은 캔버스가 콘텐츠 영역 차지, 피드백은 OCR 결과. 5개 하위 유형을 sub 파라미터로 분기

5.4 오답 인터랙션 셸 명세 S1 반영

즉시 채점이다 — 선택지를 누르는 순간 판정한다. 별도 [정답 확인] 동작은 없다.

동작구현
정답 탭pill "아주 잘 했어요!" · 소리만 재생 · 하단 [다음] 활성화. 자동 진행 없음
오답 탭pill "다시 해보세요" · 선택지 진동 · playIncorrect(). 정답 비공개, 선택지 비활성화 안 함
같은 오답 재탭진동과 소리를 매번 다시 실행. pill 문구는 같으므로 이것이 유일한 피드백이다
진동 규격과 playCorrect() 분리
  • 진동: 좌우 ±6px · 왕복 3회 · 총 300ms · ease-out · 제자리 복귀. framer-motion(^12.23.24 설치돼 있음)으로 구현.
  • playCorrect()를 그대로 쓰지 말 것. 현행 use-sound-effects.ts의 playCorrect()는 lottieEffect.playCelebration()을 함께 호출한다 — 문항마다 축하 연출이 터진다. 소리만 내는 함수를 분리하고, 축하는 결과 화면 만점일 때만.
  • playIncorrect() · /sounds/incorrect.mp3 · correct.mp3는 이미 있다 — 신규 자산 불필요.
prefers-reduced-motion 분기가 필요하다 — 현재 코드에 0건

진동 애니메이션은 전정 장애 사용자에게 불편을 준다. 전수 검색 결과 프로젝트에 prefers-reduced-motion 대응이 하나도 없다.

조건오답 신호
기본진동 300ms + 효과음 + pill
reduce진동 대신 테두리 200ms 1회 깜빡(위치 이동 없음) + 효과음 + pill

소리는 보조다 — 무음 모드·교실·청각장애가 흔하므로 소리 없이도 오답이 전달돼야 한다. 반대로 스크린리더는 진동·소리를 못 받으므로 pill을 aria-live로 두되, 같은 문구 반복 고지를 위해 영역을 비웠다 다시 채운다.

5.5 접근성 (G2 §8 — 필수)

  • 진행 세그먼트는 높이 6의 얇은 선이라 아이콘이 들어가지 않는다 — 정오답이 색으로만 남는다(Positive / Destructive / 미응답 Gray/300). 초록–빨강은 색만으로 구분되지 않으므로, 정오답의 권위 있는 표시는 피드백 pill 문구(문항 화면)와 결과 화면 오답 목록(글자)이다. 진행바는 진행 표시가 주된 일이다 — 구현 사양 §3·§13 참조.
  • 세그먼트 aria-label: i18n 키 player.a11ySegment 사용.
  • 피드백은 색 변화만이 아니라 텍스트로도 명시(player.answerIs).
  • 탭 대상 최소 44×44pt.

6i18n

동봉 파일 i18n_player_shell.ts에 5개 언어 × 30키를 작성했다(키 일치 검증 완료). 각 언어 파일 최상위에 player·result·review·state 블록을 추가하면 된다. 기존 키는 건드리지 않는다.

번역은 초안이다

특히 학습 앱 문맥에서 practice / review의 뉘앙스는 언어마다 다르다. 원어민 검수 후 확정할 것. 다만 내부 용어를 화면에 내보내지 않는다는 원칙(큐·상태·세션 금지)은 검수에서도 유지해야 한다.

① Phase 0 핫픽스를 먼저 보낸다 — 독립적이고, fill-blank가 정답만 저장하는 버그는 Phase 1의 선행조건이다(재시도형에서도 첫 시도 오답이 저장돼야 복습 큐가 동작한다). ② 목업 + 이 문서 + tokens.css + i18n 파일을 한 묶음으로 보내 공수·실현성 의견을 받는다. ③ 토큰 적용과 DB·API는 목업을 기다리지 않고 바로 시작할 수 있다.
