MY 학습 기록 — 무슨 데이터가 필요한가

결론부터: 새로 쌓을 것이 거의 없다. 필요한 값은 이미 세 테이블에 쌓이고 있고, 지금 아무도 읽지 않을 뿐이다. 읽기 API 하나면 된다. 다만 믿으면 안 되는 칸이 셋 있어서, 그걸 모르고 쓰면 화면이 거짓말을 한다. §5 의 네 가지는 모두 정해졌다.

1지금 쌓이고 있는 것

모두 api/persistence/model.py 와 실제 쓰기 경로를 따라가 확인했다.

테이블언제 쓰이나담기는 것
ko_learning_record 문항을 풀 때마다 급 · 과 · 활동 · 문항 · 고른 답 · 정오답 · 시각. 문항당 한 줄(upsert)이라 is_correct 는 마지막 답이다
ko_daily_activity 하루 한 줄 study_seconds(세션 핑에서) · words_learned · 마지막 학습 지점(급·과·활동)
ko_study_session 세션마다 duration_sec
ko_game_progress 게임 한 판마다 게임 · 단계 · 점수(max 유지)

ko_daily_activity 는 첫날부터 하루에 한 줄씩 있다. 누적을 만들 재료가 이미 다 있다는 뜻이다.

2믿으면 안 되는 칸 — 셋 다 처리 방침이 정해졌다

칸실제처리
modules_done 컬럼은 있는데 어디서도 쓰지 않는다. 늘 0 버린다
활동 완료는 ko_activity_state(Phase 1 DB #1)가 맡을 자리다
words_learned 단어 활동 답을 낼 때마다 +1. 같은 단어를 다시 풀면 또 오른다 — 배운 단어 수가 아니라 단어 문제를 푼 횟수 고친다
ko_learning_record 에서 단어 활동의 고유 문항 수를 센다. 그러면 이 칸 자체가 필요 없어진다
weeklyWords 서버가 매번 계산하는데 앱이 한 번도 안 쓴다 같이 정리
위 두 건을 고치면 근거가 사라진다

게스트 문제는 화면 쪽에서 닫혔다. user_id 에 게스트 id 가 들어가고 로그아웃하면 그 id 가 지워져 기록이 끊기는데 — 게스트는 MY 에 들어올 수 없게 했다(§5-4). 이 설계는 계정이 있는 사용자만 다룬다.

3MY 가 답해야 할 다섯 가지

홈은 이번 주만 말한다. MY 가 맡을 것은 여태까지다. 같은 숫자를 두 번 보여 주지 않는 것이 이 화면의 기준이다.

  1. 얼마나 오래 했나
    SUM(ko_daily_activity.study_seconds) 전체 기간
  2. 며칠이나 했나
    COUNT(ko_daily_activity) + 최장 연속일. 홈의 스트릭은 지금 며칠째인지만 말한다 — 최장 기록은 아직 어디에도 없다
  3. 어디까지 왔나
    ko_learning_record 를 급으로 묶어 푼 문항 수. 진행률은 앱이 나눈다(§5-3) — 서버는 푼 개수만 준다
  4. 얼마나 맞았나
    SUM(is_correct) / COUNT(*). 마지막 답 기준이라 다시 풀어 맞히면 올라간다 — 그게 이 앱의 채점 방식과 맞는다
  5. 다시 풀 것이 몇 개인가
    COUNT(is_correct = false). Phase 1 의 ko_review_queue 가 생기면 그쪽으로 옮긴다 — 없어도 지금 셀 수 있다

4제안 — 읽기 하나

새 테이블도, 새 쓰기도 필요 없다. 이미 있는 네 테이블을 합쳐 읽기만 한다.

GET /learning-summary        (로그인 사용자 전용 — 게스트는 이 화면에 들어오지 않는다)
{
  "study": {
    "totalSeconds": 48120,     // 전체 학습 시간
    "days": 37,                // 학습한 날 수
    "currentStreak": 3,        // 지금 연속 (홈과 같은 값)
    "longestStreak": 11        // 최장 연속 — 새로 계산
  },
  "answers": {
    "answered": 812,           // 푼 문항 (중복 제외 · 문항당 한 줄)
    "correct": 640,            // 마지막 답이 정답인 문항
    "words": 214               // 단어 활동의 고유 문항 수 — §2 의 고친 정의
  },
  "byBook": [
    { "bookId": 1, "answered": 340, "chapters": 12 },
    { "bookId": 2, "answered": 210, "chapters": 8 }
  ],
  "review": { "count": 172 },  // 아직 못 맞힌 문항
  "games": { "played": 4 }     // 한 번이라도 한 게임 수
}

총 문항 수가 응답에 없는 이유. 급별 총 문항 수는 앱이 이미 안다 (shared/data). 서버가 그걸 알게 하면 콘텐츠 원장이 서버로 한 발 더 가므로, 서버는 푼 개수만 주고 진행률은 앱이 나눈다(§5-3).

5정해진 것

1 · words_learned 를 고칠지, 안 보여 줄지

고친다 — ko_learning_record 에서 단어 활동의 고유 문항 수를 센다

따라오는 일: business/learning_record.py 의 incrementWordsLearned 호출을 뺀다. 그러면 ko_daily_activity.words_learned 칸은 더 이상 쓰이지 않는다

2 · modules_done 를 채울지 버릴지

버린다

참조하는 코드가 없다. 활동 완료는 ko_activity_state 가 맡는다

3 · 급별 총 문항 수를 서버가 알아야 하나

아니다 — 앱에서 나눈다

응답의 byBook 은 푼 개수만 담는다. 콘텐츠 원장은 앱에 남는다

4 · 게스트에게 이 화면을 보여 줄지

아니다 — 게스트는 MY 에 들어올 수 없다. 로그인해야 한다

이 API 는 로그인 사용자만 부른다. §2 의 게스트 id 문제가 여기서 닫힌다

64번을 넣다 찾은 것 — 앱은 이미 고쳤다

게스트가 로그인 화면에 닿을 수 없었다. 로그인 화면이 isSignedIn 인 사람을 돌려보내는데 게스트도 그 조건에 걸린다.

그런데 handleLogin 에는 게스트 기록을 방금 로그인한 계정으로 옮기는 코드(migrateGuestData)가 있다. 정확히 그걸 위해 쓰인 사람들이 그 화면에 못 가고 있었으므로, 그 경로는 한 번도 쓰이지 않았다.

이제 진짜 로그인 사용자만 돌려보낸다. 게스트가 MY 를 누르면 로그인 폼이 뜨고, 로그인하면 그동안의 기록이 계정으로 넘어간다 — 누적 학습 기록이 게스트 시절부터 이어진다는 뜻이라 이 설계와도 맞물린다.
