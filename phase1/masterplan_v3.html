3전체 지도 — 트랙과 임계 경로

4이 순서인 이유 — 판단 근거 3가지

  1. 콘텐츠는 사람이 쓰는 것이라 병렬화가 어렵다. 개발은 인력을 붙이면 단축되지만, 급별 문항 저작·검수는 리드타임이 거의 고정이다. 가장 긴 것을 가장 먼저 시작한다.
  2. 콘텐츠 저작은 화면 설계를 기다릴 필요가 없다. "4지선다 어휘 문항"의 데이터 모양만 정해지면 UI가 어떻게 생겼든 문항은 쓸 수 있다. 반대로 화면부터 잡으면 콘텐츠가 통째로 뒤로 밀린다.
  3. 개발은 콘텐츠 없이도 절반이 진행된다. 공통 셸·상태 모델·라우트 정리는 콘텐츠와 무관하다. 구 콘텐츠를 임시로 꽂아 셸을 먼저 검증할 수 있다.

값은 대조 자체가 아니라 대조가 드러낸 것에 있었다. 화면을 넣을 때마다 앱이 목업에서 벗어난 자리가 나왔다 — VocaShot 의 그리지 않던 마크업 여덟 자리, 조사 스나이퍼 과 선택의 낡은 상한(8 → 20), 게임 목록의 아이콘 색 배정이 통째로 달랐던 것(서울=파랑·카드=초록·조사=보라 → 목업은 서울=초록·카드=호박· 조사=인디고). 셋 다 목업을 따랐다. 죽어 있던 game.css 42줄 (pc-result-* · sp-complete-*)은 되살리는 쪽으로 끝났다 — 대조를 통과시키려면 컴포넌트가 목업 구조와 같아야 했기 때문이다. 남겨 둔 애매한 자리는 BLOCKERS.md §3-b 에 적었다.

넣자마자 하나 잡았다. VocaShot 시작 화면의 뒤로가기가 목업은 svg 화살표인데 앱은 글자 ← 였다. 목업이 기준이므로 앱을 고쳤다 — 대조를 넣는 값어치가 이것이다.

이게 두 번째다

게임에서 같은 일이 먼저 있었다 — 게임 목업(지금은 screens_SOT 의 게임 절)을 검증용 산출물로만 다루고 앱에 옮기는 일을 구현 목록에 넣지 않았다. 그때 원인을 "목업이 덧씌우는 층이라서"로 적었는데, 이번엔 목업을 아예 열지 않았다. 원인이 다르고, 둘 다 같은 결과를 냈다.

1단계 — 목업 CSS 를 앱으로

Tailwind 유틸리티로 숫자를 다시 옮겨 적는 방식이 이번 실패의 원인이었다. 목업이 이미 클래스와 CSS 로 디자인을 들고 있으니 그것을 정본으로 가져온다.

  • 목업의 CSS 를 앱 스타일시트로 이관 — 색은 tokens.css 의 semantic 으로 치환
  • 클래스 이름을 목업과 같게 쓴다. 그래야 대조가 눈으로 된다
  • Storybook 스토리 = 목업 화면과 1:1. 다른 상태를 새로 상상하지 않는다
