2.1 ko_activity_state — 활동 상태 신설

현재는 활동 완료를 learning_record 건수와 content_counts.TOTAL_QUESTIONS를 비교해 매번 계산한다. G2 상태 머신은 명시적 상태와 이어하기 위치가 필요하므로 별도 테이블로 승격한다.

CREATE TABLE ko_activity_state (
  id                  INT          NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id             VARCHAR(45)  NOT NULL,
  book_id             INT          NOT NULL,      -- 급 (화면 라벨만 "급", 컬럼명 유지)
  chapter_seq         INT          NOT NULL,      -- 과
  menu_type           VARCHAR(20)  NOT NULL,      -- 기존 값 그대로 사용 (아래 §2.2 참조)
                                                  -- word | fill-blank | listen-answer | read-answer
                                                  -- | roleplay | flashcard | mission-chat | jamo(신규)
  state               VARCHAR(16)  NOT NULL DEFAULT 'in_progress',  -- in_progress | completed
                                                  -- ※ 미학습은 행 자체가 없는 상태로 표현(G2 §9: 화면에도 표기 안 함)
  sub                 TINYINT      NOT NULL DEFAULT 0,   -- 하위 유형. 자모만 1~6, 나머지 활동은 0
  current_item_index  INT          NOT NULL DEFAULT 0,   -- 이어하기 위치
  total_items         INT          NULL,                 -- 전체 문항 수. 진행률의 분모
  answered_count      INT          NOT NULL DEFAULT 0,
                                                  -- ※ 응답한 문항 수. 진행률의 분자. 정오답 무관, 발음도 센다
                                                  --    건너뛴 문항과 녹음 없이 넘긴 발음 문항은 세지 않는다
  graded_count        INT          NOT NULL DEFAULT 0,
                                                  -- ※ 채점 대상 문항 수. 정답률의 분모
                                                  --    발음(자모 sub=1·3)과 플래시카드는 0 → 화면에 "—"
  correct_count       INT          NOT NULL DEFAULT 0,
                                                  -- ※ 첫 시도 기준. 재시도로 맞힌 것은 세지 않는다(셸 명세 S1)
  completed_at        DATETIME     NULL,
  created_at          DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()),
  updated_at          DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()) ON UPDATE UTC_TIMESTAMP(),
  UNIQUE KEY uq_state (user_id, book_id, chapter_seq, menu_type, sub),
  KEY ix_user (user_id)
);
sub가 없으면 자모 6종이 같은 행을 쓴다

자모는 라우트가 /learn/jamo?sub=1~6로 6개 하위활동인데 menu_type은 jamo 하나다. 키에 sub가 없으면 다섯이 한 행을 공유해서, 하나를 완료하면 나머지도 완료로 보이고 이어하기 위치가 서로 덮인다.

menu_type을 jamo-1~jamo-5로 쪼개지 않는 이유: 그러면 ko_learning_record·ko_daily_activity·content_counts의 키가 전부 5개씩 늘어난다. sub는 자모에만 의미가 있고 나머지는 0이라 기존 코드가 영향을 안 받는다.

NULL이 아니라 NOT NULL DEFAULT 0인 이유 — MySQL은 UNIQUE 키에서 NULL을 중복 허용하므로, NULL로 두면 자모 아닌 활동의 유니크 제약이 무력해진다.

"복습 권장"은 컬럼이 아니다

G2 §1에서 복습 권장은 완료의 하위 표시로 정의했다. 따라서 state에 값을 추가하지 않고, ko_review_queue에 해당 활동 소속 항목이 남아 있는지로 판정한다 — 상태를 두 곳에 쓰면 어긋난다.

채점은 첫 시도만 기록한다 셸 명세 S1 반영

선택지 활동은 재시도형으로 확정됐다 — 오답이어도 정답을 공개하지 않고 맞힐 때까지 다시 고르게 한다. 따라서 무엇을 기록하는지가 모호해질 수 있다.

  • correct_count · ko_learning_record · 진행바 칸 상태 — 전부 첫 시도 기준
  • 두 번째 이후 시도는 기록하지 않는다 (정답률이 항상 100%가 되어 무의미해진다)
  • ko_review_queue 예약도 첫 시도 오답 기준 — 재시도로 맞혀도 복습 큐에 남는다

즉 문항당 정확히 한 번만 기록된다. 재시도 횟수를 남기고 싶으면 별도 컬럼이 필요하지만, Phase 1 범위 밖이다.

2.2 menu_type 값은 바꾸지 않는다 v1.1 정정

v1 초안의 오류

2.3 ko_review_queue — 다시 풀기 목록 신설

CREATE TABLE ko_review_queue (
  id            INT          NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id       VARCHAR(45)  NOT NULL,
  book_id       INT          NOT NULL,
  chapter_seq   INT          NOT NULL,
  menu_type     VARCHAR(20)  NOT NULL,
  sub           TINYINT      NOT NULL DEFAULT 0,     -- 활동 상태와 같은 규칙
  question_id   INT          NOT NULL,     -- Phase 1은 기존 체계 유지. Phase 2에서 item_id로 이관
  reason        VARCHAR(16)  NOT NULL,     -- wrong | skipped | unknown(플래시카드 "몰라요")
  attempts      INT          NOT NULL DEFAULT 1,
  available_at  DATETIME     NOT NULL,     -- 홈 목록 노출 시각 = 오답·건너뜀 다음 날 0시(KST). 결과화면 [다시 풀기]는 이 값 무시
  created_at    DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()),
  updated_at    DATETIME     NOT NULL DEFAULT (UTC_TIMESTAMP()) ON UPDATE UTC_TIMESTAMP(),
  UNIQUE KEY uq_queue (user_id, book_id, chapter_seq, menu_type, sub, question_id),
  KEY ix_user_avail (user_id, available_at)
);
규칙 (G2 §6)구현
같은 날 재출제 방지available_at = 오답·건너뜀 발생일 다음 날 KST 00:00 건너뛴 것도 오답과 같이 내일부터 — 기획 확정 2026-08-27. 안 푼 것이니 오늘 바로 내보낼 수도 있었지만 두 갈래로 갈리면 복잡해서 같게 뒀다. 홈 목록은 available_at <= now만 노출, 결과 화면 [다시 풀기]는 무시하고 즉시 출제
제거 조건다시 풀기에서 정답 1회 → 행 삭제
재오답attempts += 1, available_at 갱신. 3회 이상은 ⓐ 결과 화면 강조 ⓑ 세션에서 먼저 출제 ⓒ 밀어내기 보호
상한 · 세션보관 60(초과 시 created_at 오래된 것부터 삭제, 단 attempts ≥ 3 보호) · 한 세션 10문항 · 홈 카드는 보관 총계(60 도달 시 "60+")
과당 26.7문항 실측 기준으로 60은 7~8과 분량 — 상한은 적정하나 한 번에 내보내면 압도한다
정렬attempts 내림차순 → created_at 오름차순. 여러 번 틀린 문항이 먼저
콘텐츠 삭제 대응조회 시 문항이 없으면 조용히 행 삭제 후 다음 항목으로
잠긴 콘텐츠(B2C)행은 유지하고 노출만 제외. 재구독 시 자동 복원

1complete의 wrongItems에 해설 문자열까지 담을지 정해졌다(2026-08-21) — 담지 않는다. 문항 조회로 따로 받는다. 오답은 과당 한 자릿수이고, 다시 풀기 세션이 이미 기존 문항 조회 경로를 쓰도록 설계돼 있어 그 경로에 해설을 얹으면 된다. 따로 부르는 왕복이 체감될 양이 아니다.
응답 계약 — explanation 은 wrongItems 에서 뺀다. 대신 문항 조회가 grammar_focus_revised(없으면 grammar_focus)를 낸다. 문법 빈칸 외 활동은 이 값이 빈다 — 화면은 없을 때를 정상으로 다뤄야 한다
2DELETE /review-queue/{id}를 남길지 개발 판단 · 권고는 서버 자동 제거. 이건 취향이 아니라 정합성 문제다 — 클라이언트가 learning-record 와 DELETE 를 둘 다 부르면 그 사이 실패가 끼어 맞힌 문항이 큐에 남거나 큐에서만 사라진다. 한 트랜잭션으로 묶으면 그 틈이 없다. DELETE 는 어드민 수동 제거용으로만 남긴다.
다만 "정답 1회로 제거" 규칙이 서버에 박히면 정책 변경이 서버 수정이 된다 — 그 대가를 안다
